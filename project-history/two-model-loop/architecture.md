# Архитектура продукта: локальное приложение для разработки функций

Версия 0.2 от 24.09.2026. Архитектура принята пользователем 24.09.2026 сообщением «ок, принимаю». План 0.1 согласован; начат E0 реализации. Актуальные модели, лимиты и пути определены в plan.md.

Направление стека: TypeScript, LangGraph, официальный SQLite-checkpointer, Codex с облачными моделями. Пользователь уточнил продуктовый сценарий: новая задача через текстовое поле или один из трёх примеров, затем показ работы и общения агентов. Пользователь подтвердил отдельную локальную папку результата для каждой задачи; применение в существующий проект в первую версию не входит.

## 1. Форма продукта

Пользователь открывает приложение в браузере на MacBook. Один локальный backend принимает задания, запускает LangGraph и отдаёт интерфейсу состояние работы. LangGraph вызывает Codex с нужными инструкциями и моделью.

Три агента имеют роли автора, ревьюера и исполнителя одобренных изменений. Они работают последовательно и используют две разные облачные модели. SQLite хранит состояние процесса; локальная папка хранит файлы, созданные при выполнении задачи.

Frontend-кандидат — React + TypeScript с Vite; backend — Node.js + TypeScript. Конкретный HTTP-фреймворк и версии зависимостей ещё не выбраны. Для готового приложения предлагается одна команда запуска и один локальный адрес. [Vite](https://vite.dev/guide/).

## 2. Пользовательский путь

| Шаг | Действие пользователя | Что пользователь получает |
|---|---|---|
| 1. Открыть приложение | Открывает главную страницу | Кнопку «Новая задача» и список ранее созданных задач |
| 2. Добавить задачу | Нажимает «Новая задача» | Текстовое поле и три готовых примера задания |
| 3. Описать задачу | Вводит свой текст или выбирает пример; при необходимости редактирует его | Готовое описание того, что нужно сделать |
| 4. Запустить | Нажимает «Запустить» | Страницу задачи с тремя агентами, их ролями и текущим статусом |
| 5. Следить за работой | Просматривает сообщения агентов и создаваемый код | Видит, кто сейчас работает, что передал другому агенту, какие замечания получены и что исправлено |
| 6. Проверить предложение | Открывает подготовленный результат и вывод ревьюера | Код, результаты тестов и перечень файлов, которые будут созданы или изменены |
| 7. Принять решение | Нажимает «Подтвердить» или «Отклонить» | При подтверждении начинается применение одобренной версии; при отказе итоговые файлы не изменяются |
| 8. Получить результат | Просматривает готовые файлы и скачивает их при необходимости | Список файлов, их содержимое и путь к локальной папке результата — предлагаемый формат выдачи |

Три примера заполняют текстовое поле и не запускают работу автоматически. Предлагаемое содержание примеров на TypeScript:

- Написать функцию объединения пересекающихся интервалов.
- Написать функцию поиска кратчайшего пути между двумя вершинами небольшого графа.
- Написать функцию перевода фразы на «кошачий язык», сохраняя знаки препинания.

Тексты примеров пока иллюстративные; перед реализацией для них нужно определить однозначное ожидаемое поведение. Пользователь также может остановить активную задачу и позже открыть её из списка. Если задача остановилась или завершилась ошибкой, на её странице видны причина и доступное действие продолжения.

## 3. Экраны

**Главная страница.** Список задач с их статусами и кнопка «Новая задача».

**Новая задача.** Одно текстовое поле, три примера и кнопка «Запустить». Язык первой версии — TypeScript.

**Страница задачи.** Три карточки агентов, текущий этап, хронологическая лента сообщений и панель файлов. Для сообщения видны отправитель, получатель и время. Ожидание ответа модели и ожидание решения пользователя отображаются различно.

**Подтверждение и результат.** На той же странице пользователь видит предложение, результаты проверки и кнопки решения. После успешного применения отображаются итоговые файлы, путь и скачивание. Действия запуска, просмотра и скачивания остаются частью одной задачи.

«Логика работы агентов» в интерфейсе — наблюдаемые действия, сообщения, обоснования в ответах, результаты ревью и изменения кода. Интерфейс не обещает показывать скрытые внутренние рассуждения модели.

## 4. Что происходит после запуска

Это внутренняя последовательность приложения, а не пользовательский путь:

1. Backend создаёт задачу и запускает граф с постоянным ID.
2. Агент-автор готовит функцию и тесты. Созданные файлы сохраняются как версия черновика.
3. Приложение выполняет проверки в рабочей копии.
4. Агент-ревьюер получает версию кода и результаты проверок. При замечаниях автор получает их и готовит новую версию; число повторов ограничено.
5. После положительного ревью граф останавливается для решения пользователя.
6. После подтверждения третий агент инициирует применение именно одобренной версии. Назначение — отдельная папка результата этой задачи, подтверждённая пользователем.
7. Приложение проверяет записанные файлы и сообщает результат.

Тесты — часть программы, а не ещё один агент. Следующий шаг выбирает LangGraph, а не frontend.

## 5. Состояние и артефакты: разные данные

**Состояние работы** отвечает на вопросы: какая задача выполняется, на каком этапе она находится, какая версия сейчас актуальна, что сказал ревьюер, получено ли подтверждение, сколько попыток осталось.

**Артефакты работы** — сами файлы: функция `.ts`, тесты, сохранённые версии и итоговый результат.

Предлагаемое распределение:

| Данные | Где хранятся | Кто отвечает |
|---|---|---|
| Состояние графа и история сохранений | Локальный файл SQLite | Готовый `SqliteSaver` LangGraph |
| Ссылки на версии файлов, результаты ревью, подтверждение и лимиты | В состоянии графа, сохраняемом в SQLite | Наше описание полей state и узлы LangGraph |
| Содержимое черновиков, рабочие копии и итоговые файлы | Локальная папка каждой задачи | Небольшой модуль работы с файлами приложения |
| События незавершённого вызова Codex | В интерфейсе через streaming; долговечное сохранение только необходимых событий уточняется | Адаптер Codex; второй механизм checkpoints не создаётся |

LangGraph сохраняет данные, которые приложение включает в state. Если положить туда текст кода, он тоже попадёт в checkpoint; это возможно, но само по себе не создаст выдаваемый пользователю файл `.ts`. Для нашего продукта предлагается хранить канонические версии артефактов на диске, а в state — ссылки на них. Это решение приложения, а не требование LangGraph. [Документация Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers).

### Предлагаемая структура локальных данных

Ниже пример структуры, а не уже созданные папки. Корневая папка принята в plan.md: `.local-data/` в рабочем корне. В примере ниже `app-data/` обозначает именно её.

```text
app-data/
  checkpoints.sqlite
  tasks/
    task-001/
      revisions/
        v001/
          solution.ts
          solution.test.ts
        v002/
          solution.ts
          solution.test.ts
      work/
      result/
        solution.ts
        solution.test.ts
```

`revisions` содержит неизменяемые версии предложений. `work` используется для запуска проверок. `result` содержит только одобренный итог; до подтверждения в него не публикуется результат. Рабочие файлы приложения существуют и до подтверждения — это не изменение итоговой папки или пользовательского проекта.

Ссылка в состоянии включает ID задачи, ID версии, путь относительно папки данных и контрольную сумму содержимого. Одного пути к перезаписываемому файлу недостаточно: прежнее ревью и подтверждение должны относиться к тем же байтам после перезапуска.

### Сохранение и восстановление файлов

Версия сначала полностью записывается на диск, затем ссылка на неё сохраняется в state. При продолжении приложение проверяет наличие файлов и соответствие версии. Потерянный или изменённый файл отображается как проблема, а не как готовый результат.

SQLite и файловая система не являются одной общей транзакцией. Если процесс прерван при публикации результата, приложение сверяет записанные файлы с подтверждённой версией. Это узкая обязанность файлового модуля, не собственная реализация сохранения графа.

Для переноса всей задачи с историей нужны база и папки артефактов. Для выдачи пользователю результата достаточно файлов из `result`.

### Получение результата пользователем

Предложение для первой версии: приложение само создаёт папку задачи внутри известной корневой папки. На странице результата показывает имена файлов, предпросмотр содержимого, полный путь с кнопкой копирования и возможность скачать файл или комплект.

Браузер получает содержимое через backend по ID артефакта. Локальный путь служит подсказкой пользователю; сам по себе он не является ссылкой скачивания. Кнопка открытия Finder не включена автоматически и может обсуждаться отдельно.

Применение в существующий проект пользователя не входит в первую версию: пользователь выбрал отдельную папку результата задачи.

## 6. Что предоставляет LangGraph

Используем официальный пакет `@langchain/langgraph-checkpoint-sqlite`: подключаем `SqliteSaver`, указываем файл базы и передаём checkpointer графу. LangGraph управляет сохранениями; своё хранилище checkpoints не пишем. Состояние и историю читаем через `getState` и `getStateHistory`. [Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers), [официальный пакет](https://github.com/langchain-ai/langgraphjs/tree/main/libs/checkpoint-sqlite).

Хранение в памяти не подходит для перезапуска приложения. Для передачи событий внешнего Codex-процесса используем возможности streaming; это не автоматическое долговечное сохранение каждого события. [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence), [Streaming](https://docs.langchain.com/oss/javascript/langgraph/streaming).

## 7. Модули приложения

| Модуль | Ответственность |
|---|---|
| Frontend | Новая задача, примеры, ход работы, просмотр файлов, подтверждение, получение результата |
| Локальный API | Команды пользователя, состояние задачи, события, выдача файлов |
| LangGraph | Порядок работы ролей, доработки, остановка, ожидание решения, продолжение |
| Адаптер Codex | Вызовы моделей, ограниченный контекст, события, ошибки и отмена процессов |
| Подключение SqliteSaver | Настройка готового сохранения графа и чтение через API LangGraph |
| Файлы и проверки | Запись версий, подготовка рабочей копии, тесты, проверка подтверждения и публикация результата |

Это модули одного локального backend, а не отдельные серверы. Дополнительный универсальный сервис хранения файлов не нужен.

## 8. Связь интерфейса и выполнения

API возвращает ID принятой задачи, а граф работает независимо от длительности HTTP-запроса. Для обновлений предложен SSE, для команд — обычные HTTP-запросы. После переподключения frontend получает актуальное состояние и недостающие события. Точный протокол и библиотека API определяются в плане.

Закрытие вкладки не прекращает backend. Закрытие backend прекращает работу; новый запуск восстанавливает сохранённый этап. Неизвестный исход незавершённого вызова показывается пользователю явно. Проверка исходного задания включает остановку backend, а не только закрытие вкладки.

Backend слушает локальный адрес и обращается только к разрешённой папке данных/проекта. Учётные данные остаются у Codex и не попадают в frontend, артефакты или окружение тестов. Полная история работы недоступна агентам как папка для произвольного чтения; контекст составляется из актуальных данных задачи.

## 9. Статус согласования

Пользователь принял описанный продукт и выдачу файлов: отдельная папка результата, просмотр, путь и скачивание. Разрешено перейти к плану разработки. Конкретное стандартное расположение данных, модели, версии зависимостей и численные лимиты фиксируются как предложения в плане; произвольные проекты и пути на каждую задачу не добавляются.
