# Варианты управления циклом трёх агентов

Проверено 24.09.2026. Основание: ТЗ 0.3 и сообщение координатора о его согласовании. Исследование ограничено оркестрацией; аутентификацию Codex и доступность моделей проверяет координатор. Код не изменялся, проекты не устанавливались, платные вызовы не выполнялись. Использован навык research; дополнительная делегация не выполнялась согласно поручению.

> Обновление после обсуждения: первоначальная рекомендация ниже пересмотрена в пользу LangGraph. Актуальные выводы: [подробное сравнение](research-langgraph-comparison.md) и [проверка отладки](research-langgraph-debugging.md). Текст ниже сохранён как след первоначального исследования.

## Первоначальный вывод для обсуждения

Рекомендую небольшой последовательный координатор на TypeScript с локальной SQLite: готовый компонент хранения, собственные переходы между автором, ревьюером, ожиданием подтверждения и применяющим агентом. Это рекомендация, не выбранная архитектура. Для одной задачи и фиксированных трёх ролей наиболее трудные обязательные части — журнал подтверждённых событий, обработка неизвестного исхода запроса и привязка разрешения к версии — всё равно остаются прикладным кодом при любом фреймворке.

LangGraph JS — разумная альтернатива, если важнее использовать готовые checkpoints и interrupts и команда готова объяснять их семантику. OpenAI Agents SDK полезен для свободной передачи управления между агентами, но для жёсткого сценария преимущества handoffs невелики; возможность подходящего подключения здесь не оценивалась.

## Проверенные кандидаты

### 1. Собственный координатор + SQLite

Переиспользуемый компонент — транзакционное хранилище SQLite. SQLite документирует ACID-транзакции; это позволяет атомарно фиксировать переход состояния и запись события **внутри базы**, но не делает сетевой запрос или запись исходников частью этой транзакции. [Транзакционность](https://www.sqlite.org/transactional.html).

Код SQLite находится в public domain, а не «без разрешения на использование». Документированы автоматизированные тестовые комплекты; последняя верхняя запись открытой истории релизов — 3.53.4 от 24.07.2026. [Условия использования](https://www.sqlite.org/copyright.html), [тестирование](https://www.sqlite.org/testing.html), [релизы](https://www.sqlite.org/changes.html).

Встроенный `node:sqlite` существует с Node 22.5; в открытой документации Node 26.10 он имеет статус release candidate. Поэтому отсутствие отдельного npm-драйвера не означает стабильный API на любой установленной версии Node. Конкретную версию Node и встроенной SQLite нужно зафиксировать при выборе стека; альтернатива — отдельно проверенный драйвер. [Node SQLite](https://nodejs.org/api/sqlite.html).

Совместимость с TypeScript/MacBook: ожидается при выбранной поддерживаемой версии Node, но локальная проверка в это исследование не входила. Зависимости самого координатора могут ограничиться транспортным адаптером и драйвером/встроенным модулем БД. Тесты координатора необходимо написать самостоятельно. Сложность: меньше сторонних понятий, больше ответственности за корректность переходов и восстановления.

### 2. LangGraph JS

Переиспользуемые компоненты — `StateGraph`, постоянный checkpointer и `interrupt`/`Command`. Checkpointer хранит состояние потока; `MemorySaver` теряет его после перезапуска, для локальной задачи нужен файловый `SqliteSaver`. Checkpoint сам по себе не сокращает сообщения модели. [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence).

`interrupt` сохраняет точку ожидания внешнего решения; продолжение использует прежний `thread_id`. При возобновлении узел начинается сначала, поэтому код до interrupt выполняется повторно: применение файлов следует вынести после отдельного подтверждения и защитить от повторного исполнения. [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts).

Есть `recursionLimit`: ограничение super-steps одного выполнения с ошибкой `GraphRecursionError`. Это не общий пожизненный счётчик задачи: для перезапусков нужен собственный сохранённый бюджет. [Graph API, первичный исходник документации](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/graph-api.mdx).

Репозиторий лицензирован MIT. На открытой странице релизов виден свежий prerelease `@langchain/langgraph@1.4.18-rc.0` от 22.09.2026; это свидетельство сопровождения, не рекомендация брать RC. Последний стабильный тег в рамках просмотра не установлен. [Репозиторий](https://github.com/langchain-ai/langgraphjs), [LICENSE](https://github.com/langchain-ai/langgraphjs/blob/main/LICENSE), [релизы](https://github.com/langchain-ai/langgraphjs/releases).

SQLite-checkpointer в main имеет версию 1.0.4, зависит от `better-sqlite3 ^12.10.0`, имеет peers `@langchain/core` и `@langchain/langgraph-checkpoint`; объявлены Vitest unit/integration scripts. Основные пакеты используют TypeScript; совместимость нативного SQLite-драйвера с конкретными Node/macOS требует проверки установки. Наличие scripts не является доказательством зелёного CI. [Manifest checkpointer](https://raw.githubusercontent.com/langchain-ai/langgraphjs/main/libs/checkpoint-sqlite/package.json), [manifest core](https://raw.githubusercontent.com/langchain-ai/langgraphjs/main/libs/langgraph-core/package.json).

Сложность интеграции оцениваю как среднюю: схема состояния, граф, SQLite, отдельный журнал транспортных событий, компактный prompt и проверка разрешённой версии. Сервер и облачный сервис LangSmith для предложенного варианта не закладываются.

### 3. OpenAI Agents SDK JS — готовые handoffs/tools

`Runner` поддерживает handoffs, `maxTurns`, отмену через `AbortSignal`, обработку входа `callModelInputFilter`. При handoff сохраняется накопленная история: ограничение контекста нужно задавать явно. Лимит отдельного run не заменяет общий сохранённый счётчик задачи. [Running agents](https://openai.github.io/openai-agents-js/guides/running-agents/).

Approval-поток возвращает interruptions и сериализуемый `RunState`; его можно сохранить и позднее восстановить. Документация поддерживает approval в handoffs и вложенных `agent.asTool()`. Это готовая пауза выполнения, но соответствие одобрения конкретной версии исходников и текущей базе остаётся задачей приложения. [Human in the loop](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/).

Sessions сохраняют историю разговора; они отличаются от контрольной точки незавершённого выполнения. Для потоковых событий есть отдельный streaming API; локальный журнал и возраст ожидания необходимо построить поверх него. [Sessions](https://openai.github.io/openai-agents-js/guides/sessions/), [Streaming](https://openai.github.io/openai-agents-js/guides/streaming/).

MIT; последний релиз на открытой странице — 0.18.0 от 10.09.2026. Manifest пакета включает `agents-core`, `agents-openai`, `agents-realtime`, `debug`, `openai ^7.2.0`, peer `zod ^4`. В репозитории объявлены Vitest, coverage и integration checks; фактические результаты CI не проверялись. [Репозиторий](https://github.com/openai/openai-agents-js), [LICENSE](https://raw.githubusercontent.com/openai/openai-agents-js/main/LICENSE), [релизы](https://github.com/openai/openai-agents-js/releases), [manifest](https://raw.githubusercontent.com/openai/openai-agents-js/main/packages/agents/package.json), [test scripts](https://raw.githubusercontent.com/openai/openai-agents-js/main/package.json).

Сложность интеграции оцениваю как среднюю/повышенную именно для заданного сценария: потребуется согласовать lifecycle runner с собственным долговечным состоянием. Адаптация примерного HITL-проекта полезна как ориентир; копирование целого проекта не убирает обязательные прикладные проверки.

## Сравнение относительно приёмки

| Свойство | Собственный координатор | LangGraph JS | Agents SDK JS |
|---|---|---|---|
| R-04: прекращение обмена | Сохранённый предел попыток, тайм-аут, явная причина | Встроенный recursionLimit плюс общий бюджет задачи | maxTurns/AbortSignal плюс общий бюджет задачи |
| R-05: отправка, доставка, отсутствие ответа | Собственная модель событий адаптера | События графа не доказывают приём поставщиком | Streaming не заменяет долговечный журнал приёма |
| R-06: продолжение | SQLite хранит этап, результат и незавершённую попытку | Постоянный checkpointer; учитывать повтор узла | Сериализация RunState для поддерживаемых пауз; session не равна checkpoint |
| R-06: ограниченный вход | Явный компактный пакет | Явный выбор полей состояния для prompt | Явный input filter/подготовка входа |
| A-08: только подтверждённая версия | Собственная проверка версии перед применением | interrupt плюс такая же проверка | needsApproval плюс такая же проверка |

## Минимальная предлагаемая конструкция и риски

1. Одна активная задача, три фиксированные роли, последовательные переходы. Все попытки учитываются в сохранённом счётчике, включая повтор после неизвестного исхода; перезапуск не обнуляет лимит.
2. До запроса сохранить intent с `taskId`, `attemptId`, ролью, моделью, временем и хешем входа. Различать «подготовлено», «передано локальному адаптеру», «приём подтверждён источником X», «получен ответ», «тайм-аут/исход неизвестен». Не называть запуск subprocess доставкой облачной модели. Доступные подтверждения зависят от транспортного исследования координатора.
3. Сохранять законченный ответ и следующий этап атомарно. После аварии незавершённая попытка остаётся неизвестной; сначала попытаться получить её результат, если транспорт это поддерживает. Иначе показать неопределённость и применить согласованную политику повторов. Exactly-once облачный вызов не обещать.
4. Полная переписка — аудит. Вход следующего вызова — отдельный измеряемый пакет: задача, действующие ограничения, актуальная версия функции/тестов, последнее релевантное ревью, краткий статус. Предложение бюджета для обсуждения: 32 KiB UTF-8; переполнение останавливает вызов с объяснением, а не обрезает код молча. Checkpoint может быть большим; нельзя объявлять его наличие доказательством компактного контекста. Дополнительно проверить отсутствие скрыто подставленной транспортом старой истории.
5. Approval хранит `taskId`, `revisionId`, хеш точных байтов артефакта и хеши исходного состояния целевых файлов. Любое изменение версии либо базы аннулирует прежнее разрешение. Для третьего агента предлагается узкий инструмент `applyApprovedRevision(id)`: он инициирует применение, а проверенный код записывает только сохранённые байты. Свободное переписывание функции третьей моделью нарушает гарантию совпадения.
6. База и файловая система не образуют общей транзакции. Нужен журнал применения с фазами и сверкой хешей при восстановлении; для двух файлов возможна частичная запись. Ограничить список путей и явно проверить прерывание между записями. Успех означает совпадение всех конечных хешей и пройденные согласованные тесты, а не только завершение агента.

## Что обсудить до плана

- Принимается ли третий агент с узким инструментом применения неизменённого артефакта? Это сохраняет роль агента и позволяет доказать точное совпадение.
- Предлагаемые численные границы: 32 KiB входа и конечный общий предел попыток; число попыток и тайм-аут выбрать после проверки реального транспорта.
- Политика неизвестного ответа: рекомендуемый минимум — явная остановка и продолжение оператором с сохранённого этапа, без скрытого повторного запроса; если требуется полностью автоматическое восстановление, согласовать ограниченный повтор с риском дублирования облачной работы.

Факты документации проверены веб-инструментом. Совместимость установленного окружения, реальные сбои, скорость и результаты тестов кандидатов не проверялись. Перед фиксацией зависимостей нужно выбрать стабильные версии и сопоставить используемые API именно с их тегами: документация/main могут опережать релиз.
