# Подробное сравнение: свой координатор и LangGraph JS

24.09.2026. Документальное исследование по запросу пользователя; прототипы не создавались, объём кода и время разработки не измерялись. ТЗ 0.3 сохраняется. Этот документ уточняет и заменяет прежнюю рекомендацию research.md.

## Вывод

Для согласованного сценария **рекомендую LangGraph JS с локальным SQLite-checkpointer и адаптером Codex**. Пользовательский аргумент о повторном использовании persistence и human-in-the-loop обоснован: эти механизмы входят в обязательную часть задачи, а не являются возможностями на будущее.

Предыдущее рассуждение «самое сложное всё равно придётся писать самим, значит свой координатор проще» было недостаточным. Общий прикладной код нужен в обоих вариантах; поверх него собственный координатор требует ещё реализации механизма исполнения и восстановления. Небольшое число ролей не делает восстановление после аварий бесплатным.

Не утверждаем, что LangGraph гарантированно даст минимальное число строк. Для этого нужны сопоставимые реализации с одинаковыми проверками. Но на уровне ответственности он снимает конкретные блоки собственного кода и тестов, поэтому сейчас аргументов в его пользу больше.

## Что именно сравниваем

А: TypeScript + свой механизм переходов/пауз/восстановления + SQLite + адаптер Codex.

Б: TypeScript + LangGraph StateGraph + SqliteSaver + тот же адаптер Codex.

SQLite — хранилище в обоих случаях. LangGraph отвечает за исполнение процесса, а Codex — за доступ к моделям. Не требуется поднимать локальные модели, покупать отдельный API-доступ или переносить контур в облачный сервис LangChain. Узлы LangGraph могут быть обычными async-функциями, поэтому вызов CLI внутри узла — допустимая конструкция, хотя её интеграцию ещё нужно проверить. [Graph API](https://docs.langchain.com/oss/javascript/langgraph/graph-api).

OpenAI Agents SDK исключён из текущего сравнения по пожеланию пользователя. LangGraph SDK для общения с развёрнутым Agent Server и библиотека исполнения графа — разные слои; для базового контура предлагаем именно локальную библиотеку `@langchain/langgraph`.

## Матрица собственного кода

| Часть | Собственный координатор | LangGraph | Где преимущество |
|---|---|---|---|
| Порядок автор → ревьюер → человек → применение | Собственный dispatcher, переходы, допустимость состояний | Описать узлы и рёбра; выполнять их будет библиотека | Умеренное преимущество LangGraph; сам порядок прост |
| Сохранение этапов и результатов | Схема БД, сериализация, точки записи, восстановление следующего действия | Настроить постоянный checkpointer и схему state | Сильное преимущество LangGraph |
| Пауза для человека, переживающая закрытие процесса | Сохранить запрос решения, ожидание, ответ и путь продолжения | `interrupt()` и `Command({resume: ...})` | Сильное преимущество LangGraph |
| История состояний и просмотр следующего действия | Проектировать историю и запросы просмотра | Готовые `getState` / `getStateHistory` | Преимущество LangGraph |
| Разветвление после отрицательного ревью | if/switch и сохранение перехода | Условное ребро | Небольшая разница |
| Конечное число итераций | Счётчик и условие остановки | Свой общий счётчик + встроенный `recursionLimit` как дополнительная защита | Небольшая экономия; правила остаются нашими |
| Таймауты и обработка ошибок | Собственная обвязка ожидания/ошибок | В актуальной документации есть настройки timeout/errorHandler | Преимущество LangGraph при подтверждении выбранной версии |
| Завершение зависшего процесса Codex | Управление дочерним процессом | То же; ошибка узла не гарантирует прекращение subprocess | Одинаковая ответственность адаптера |
| Отправка, получение, отсутствие ответа и возраст | Собственные события и смысл статусов | Пользовательские события поверх встроенного streaming/state | Частичная экономия представления, но не логики доставки |
| Компактный вход модели | Собрать и ограничить пакет | Собрать пакет из полей state | Практически одинаково |
| Проверка одобренной версии перед записью | Проверка версии, файлов и разрешения | Та же проверка после готовой паузы | Одинаковая прикладная логика |
| Прерывание во время записи файлов | Сверка фактического результата и восстановление | Та же сверка: checkpoint не транзакция файловой системы | Одинаково |
| Зависимости и понятия | Меньше внешних API, больше собственного кода | Checkpoints, reducers, interrupts, семантика повторов и версии пакетов | Преимущество своего варианта в числе зависимостей |

Матрица — инженерная оценка, не измерение строк или часов. Основания: [persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence), [checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers), [interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts), [fault tolerance](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance).

## Human-in-the-loop: что готово и что остаётся

Для нашего сценария отдельный узел подтверждения показывает версию функции/тестов и ждёт решения. После перезапуска пользователь отвечает, исполнение идёт к применению либо завершается отказом. Механизм паузы и передачи ответа предоставляет LangGraph.

Наши правила: что именно показываем, какую версию подтверждаем, как обнаруживаем изменение файлов после показа. Это небольшой предметный слой; наличие этих правил не является аргументом писать механизм паузы самостоятельно.

При resume узел с interrupt выполняется заново с начала. Поэтому генерацию кода и запись файлов нельзя ставить перед interrupt в том же узле. Разделение «подготовка → подтверждение → применение» уменьшает риск повторного побочного эффекта. [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts).

## Persistence: четыре разных случая

| Момент закрытия | Что даёт LangGraph | Что проверяем сами |
|---|---|---|
| Между завершёнными этапами | Продолжение из сохранённого состояния | Постоянный SQLite-checkpointer, тот же thread_id, действительно завершённая запись |
| Во время ожидания подтверждения | Восстановление паузы | Показ той же версии, отказ/отсутствие решения не запускает запись |
| Во время облачного вызова | Возврат к сохранённому графу | Незавершённый вызов может иметь неизвестный исход; не выдавать его за успех и не повторять бесконтрольно |
| Во время записи исходников | Возврат к состоянию применения | Сверить файлы; не допустить повторного применения к другой базе или ложного успеха |

В первых двух строках библиотека берёт основную механическую работу. В последних двух не может устранить разрыв между локальным сохранением и внешним эффектом. Собственный координатор сталкивается с тем же разрывом, поэтому это ограничение обоих вариантов, а не недостаток только LangGraph.

Документация описывает постоянное хранение и fault tolerance; реальное закрытие процесса нужно проверять на выбранном checkpointer и режиме сохранения. Graceful shutdown, когда процесс успевает завершить шаг, не заменяет проверку внезапного прерывания. [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence), [fault tolerance](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance).

## Сообщения и ограниченный контекст

Необязательно строить чат, где каждый узел добавляет всю переписку в messages. Для этой задачи state может хранить: запрос функции, текущую версию кода и тестов, последнее ревью, число попыток, подтверждённую версию, состояние текущего вызова. История checkpoints остаётся доступной для отладки, а модели передаётся только нужная часть текущего state.

Таким образом, в LangGraph компактный контекст не «отсутствующая возможность», а наша политика выбора данных. Код такой политики нужен и в собственном решении. Существование большого архива на диске не означает передачу архива модели. Контролируемая папка и новые вызовы Codex по-прежнему должны исключать незаметное восстановление всей старой сессии.

LangGraph управляет передачей состояния между узлами. Это не обещание наблюдаемой доставки запроса в удалённую модель. Для требования «что дошло» показываем границу подтверждения: локальный адаптер принял задание, Codex выдал событие, получен ответ. Локальный приём не переименовываем в подтверждённый облачный приём.

Для показа ожидания во время незавершённого узла нужны время начала и события адаптера. Обновление state только при возвращении результата узла слишком поздно. Следует сохранять подготовку попытки до внешнего вызова и, при необходимости, компактный локальный журнал его событий. Такой журнал не должен превращаться во второй самостоятельный механизм исполнения графа.

## Отладка и проверка

LangGraph позволяет повторно использовать средства просмотра состояния и исполнения вместо собственного набора SQL-запросов и отладочных команд. Подробности локального просмотра, Studio и LangSmith вынесены в [отдельную проверку](research-langgraph-debugging.md).

У своего координатора отладка обычным Node debugger проще в смысле числа абстракций. Но расследование «какой этап был сохранён перед закрытием» потребует собственных инструментов, которые LangGraph уже предлагает. Для этой задачи история выполнения важнее экономии нескольких абстракций.

С LangGraph не нужно заново проверять всю внутреннюю реализацию библиотеки. Нужны интеграционные проверки нашей конфигурации: прерывание, восстановление паузы, повтор узла и поведение выбранного SqliteSaver. Проверки подмены версии, зависшего Codex, утечки полной истории и отсутствия подтверждения остаются в обоих вариантах.

## Где свой координатор был бы предпочтительнее

- Команда уже имеет готовый проверенный механизм состояния и возобновления: писать его повторно не нужно.
- Нельзя добавлять зависимости LangGraph или подходящий checkpointer не работает в целевом окружении.
- Нужно специфическое управление выполнением, которое библиотека существенно усложняет.
- По результатам одинакового минимального эксперимента библиотечный вариант оказывается сложнее.

В текущем исследовании ни одно из этих условий не подтверждено. Поэтому прежнее предпочтение собственного координатора снимается.

## Рекомендация и границы следующего шага

Предлагается выбрать локальный LangGraph StateGraph + SqliteSaver + Codex CLI adapter. Граф — единственный владелец процесса; state содержит только нужные предметные поля. Не создавать поверх LangGraph дублирующий координатор. Studio и облачный tracing не делать обязательными для запуска и сдачи.

Перед реализацией в план включить короткие проверки выбранных стабильных версий: SQLite сохраняет состояние между двумя процессами; interrupt возобновляется без повторного вызова автора; события Codex видимы при отсутствии ответа; отмена узла прекращает дочерний процесс. Это условия проверки рекомендации, а не выполненные тесты.

Пользователь попросил углублённое сравнение и выразил предпочтение LangGraph; окончательный выбор архитектуры ещё не объявлен. План реализации пока не готовится.
