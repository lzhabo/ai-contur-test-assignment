# Наблюдение, сложная задача и проверка циклов

Это инструкция для оператора. Тестовый адаптер помечен в интерфейсе; его ответы не являются облачными. Один backend работает с одной папкой данных. Для каждого сценария используйте отдельную папку и свободный порт; завершайте терминальный сервер Ctrl+C. Новую папку можно получить, изменив суффикс команды, без удаления прежних данных.

## Увидеть настоящую последовательность доработки в управляемом тесте

```sh
APP_CODEX_MODE=fake APP_FAKE_SCENARIO=review_once APP_DATA_DIR=.local-data/demo-revision-v2 APP_PORT=4330 npm start
```

Откройте http://127.0.0.1:4330 и выберите «Объединить интервалы». Первая версия намеренно не объединяет соприкасающиеся интервалы: [[1,2],[2,4]] вместо [[1,4]]. Проверка обнаружит ошибку, ревьюер вернёт конкретное замечание, автор исправит сравнение границ во второй версии. Ожидается 4 вызова до решения пользователя, 2 версии, пройденные проверки последней версии, отсутствие result. В схеме и истории ревью остаются оба прохода даже после их быстрого завершения. Этот дефект вводится только в fake, не в реальную работу модели.

## Цикл ревью, который никогда не одобряет

```sh
APP_CODEX_MODE=fake APP_FAKE_SCENARIO=review_loop APP_DATA_DIR=.local-data/demo-limit-v2 APP_PORT=4331 npm start
```

Выберите один из трёх базовых примеров. Ревьюер всегда требует доработку. Ожидается остановка после 3 версий и 6 вызовов с причиной «Исчерпан лимит версий функции», без подтверждения и без result. Седьмой вызов здесь не нужен: раньше срабатывает лимит версий. После перезапуска с той же папкой счётчики не должны обнулиться.

Общий бюджет 7 вызовов нужен дополнительно: ручной повтор неизвестного исхода также расходует попытку. Его исчерпание с перезапуском проверяется в tests/integration/demo-observability.test.ts. Нельзя тестировать защиту просьбой к реальной модели «зациклись»: она может проигнорировать просьбу или одобрить результат, и это не докажет ограничитель.

## Отсутствие ответа

```sh
APP_CODEX_MODE=fake APP_FAKE_SCENARIO=no_response APP_DATA_DIR=.local-data/demo-wait-v2 APP_PORT=4332 npm start
```

Запустите базовый пример. Видны активная роль, время ожидания и последнее наблюдение. Через 30 секунд появляется предупреждение. Можно остановить задачу; можно остановить backend и запустить с той же папкой. После неопределённого исхода автоматического повтора нет; явный повтор увеличивает счётчик. Через 180 секунд ожидание одного вызова прекращается. Для быстрой автоматической проверки тесты используют уменьшенный лимит времени, не меняя настройки приложения.

## Бесконечная функция — другой случай

`while (true) {}` внутри сгенерированной функции проверяет QuickJS timeout, а не число проходов графа. Память также ограничена. Автоматические проверки:

```sh
npm test -- tests/integration/demo-observability.test.ts tests/unit/checks/quickjs-runner.test.ts
```

Для полного набора: `npm run typecheck`, `npm test`, `npm run build`.

## Сложная реальная задача

На главной странице отдельная кнопка «Сложный пример: расчёт корзины» заполняет поле, но не запускает моделей. Полный текст находится в src/shared/advanced-example.ts. Требуется распределить скидку в целых копейках пропорционально стоимости, корректно раздать остатки, учитывать исключённые товары, количество, некорректный JSON и неизменность входа; минимум 15 тестовых случаев.

Она существенно сложнее замены слов, но не гарантирует замечаний. Ревьюер может честно одобрить первый вариант. Для доказательства механики доработки используйте review_once; для оценки качества моделей — сложный реальный запрос. Сложный пример предназначен для real; fake выдаёт заранее подготовленные функции базовых примеров и не решает произвольный текст.

## Настоящее ревью заведомо ошибочной версии

```sh
npm run test:live-review
```

Это отдельный добровольный прогон с облачными вызовами через сохранённый вход Codex. Первая «авторская» попытка **подменяется явно помеченным fixture**: функция лишь копирует интервалы, а её два собственных теста проходят. Независимые проверки заранее устанавливают ошибку на пересекающихся, соприкасающихся и неотсортированных интервалах. Далее настоящий `gpt-6-luna` ревьюит эту версию, настоящий `gpt-6-sol` получает его замечание и исправляет код, а Luna ревьюит новую версию. Таким образом, три из четырёх учтённых графом попыток являются облачными вызовами. Исходную ошибочную версию нельзя представлять как самостоятельный ответ Sol.

PASS требует: конкретного `changes_requested` от настоящего ревьюера при **успешных самотестах**, изменённого кода автора, успешных независимых граничных проверок, повторного `approved` и паузы на решении человека без опубликованного результата. Скрипт сохраняет JSON-отчёт и папку задачи в новом `.local-data/live-review-feedback-*`; при сбое сохраняется то, что удалось наблюдать. Отказ модели, тайм-аут или недоступность облака показываются как неуспешный прогон, а не маскируются имитацией. Перед запуском проверьте `codex login status` и поддерживаемую версию CLI.

## Что смотреть в базе и логах

LangGraph сохраняет checkpoint в checkpoints.sqlite, а не отдельную строку бизнес-таблицы на каждый узел. Диагностический журнал показывает ID задачи/попытки/узла, подтверждённую запись checkpoint и изменения значимых полей состояния. Отдельное событие завершения узла ещё не является доказательством записи в SQLite. Исходный текст задачи, код и авторизация не должны попадать в этот журнал.

Пользовательские сообщения находятся в tasks/<id>/events.jsonl; версии и результат — в файловых папках. Они не являются дополнительными SQL-таблицами. Подробный формат и путь диагностического журнала описаны в README после реализации.
