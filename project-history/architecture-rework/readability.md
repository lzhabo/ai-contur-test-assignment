# Читаемость функций и тестов

Обязательные требования пользователя к новой реализации.

## Русские комментарии

Каждая добавленная или переписанная функция, метод и callback получает короткое объяснение на русском. Для именованных функций и методов — комментарий перед объявлением. Для анонимной функции — непосредственно перед ней или в начале тела; у callback теста поясняется проверяемый сценарий.

Комментарий описывает назначение и основные действия: какие данные функция получает, что делает и что возвращает либо изменяет. Ожидание, отмена, запись на диск, ошибки и восстановление поясняются, когда они существенны. Не требуется построчный пересказ очевидных выражений. При изменении поведения обновляется и комментарий.

Требование распространяется на production-код и тестовые помощники. При переносе неизменённой функции в новую структуру её также снабжаем русским пояснением. Сохранённые исходники задания, примеры сгенерированного кода, архивы и доказательства прежних прогонов не редактируем ради этого правила.

## Папка тестов

Используем существующую корневую `tests/`: unit, integration, e2e, fixtures и отдельно запускаемые live-пробы. Общая техническая подготовка размещается в компактном `tests/support/`; новые вложенные группы добавляются по понятной обязанности, без зеркалирования каждого production-файла.

## Как должен читаться тест

1. Русское название сообщает условие и ожидаемый результат.
2. Подготовка показывает существенные входные данные.
3. Затем идёт пустая строка и действие, которое проверяем.
4. Затем идёт пустая строка и конкретные `expect` результата или ошибки.
5. Для многошаговых сценариев повторяется «действие → проверка»: до перезапуска, после перезапуска, после явного повтора. Не нужно искусственно переносить все проверки в конец.

Один тест проверяет одно правило или связный сценарий. Несвязанные сценарии разделяем; смысловые concurrency/recovery-сценарии сохраняем целиком. Одна строка не содержит несколько самостоятельных действий через `;`.

## Уменьшение повторов без скрытия сценария

В помощники можно вынести временную папку, создание тестового приложения, учёт и закрытие ресурсов, управляемые ответы моделей, ожидание явно указанного состояния. Их имена и комментарии раскрывают действие. Очистка выполняется даже при падении проверки.

В тесте остаются: создание задачи, отправка решения, остановка, перезапуск, входные данные нарушения и ожидаемые значения. Избегаем помощников вроде `runEntireScenarioAndAssertEverything`, множества boolean-параметров и универсального test framework.

Ожидание асинхронного состояния имеет deadline и понятное сообщение с последним наблюдаемым состоянием. Произвольные sleeps для синхронизации заменяются явными сигналами или ожиданием условия; отрицательные временные проверки допускают обоснованный интервал.

## Ожидаемые ошибки

Асинхронный вызов можно сохранить в переменную с функцией, чтобы отделить описание действия от проверки и не оставить отклонённый Promise без обработчика:

```ts
// Отправляет повторное создание с занятым ключом и другим текстом задачи.
const createConflictingTask = () => service.createTask(
  { text: 'Другая функция' },
  'same-request',
);

await expect(createConflictingTask()).rejects.toMatchObject({
  code: 'idempotency_conflict',
});
```

Этот фрагмент предполагает явную подготовку исходной задачи в теле теста. Проверяем конкретный код/тип ошибки; `.rejects.toThrow()` без уточнения недостаточен, когда посторонняя ошибка могла бы ложно удовлетворить тест. Текст сообщения проверяется, если его содержание является частью контракта.

## Приёмка

- Сценарий понятен по телу теста без переходов через цепочку помощников.
- Существенные данные, действия и ожидаемые результаты видимы и разделены пустыми строками.
- Новые и перенесённые функции объяснены по-русски, комментарии соответствуют коду.
- Проверки поведения Express-базы сохранены, включая отрицательные и аварийные сценарии.
- Форматирование не уплотняет код ради лимита строк; оценки читаемости выполняет reviewer, а не только линтер.

## Найденные примеры для переработки

На Express-базе `04b956c` независимый QA отметил:

- `tests/integration/service.test.ts:40`: один тест проверяет устаревшее решение, конкурентное подтверждение и повтор после завершения. Разделить на три названных сценария; команду `decide` убрать из вложенного выражения внутри `expect` успешного результата.
- `tests/integration/http-events.test.ts:68` и `:85`: смешаны origin, идемпотентность, cursor, отсутствующая задача, JSON parser, Content-Type, размер тела и HEAD. Разделить по правилам; небольшие таблицы оставить только для однородных входов.
- `tests/unit/web/workflow.test.tsx:7` и `:9`: большие однострочные данные скрывают порядок событий, версии и ревью. Назвать значимые события, раскрыть объекты, разделить тест модели истории и рендера.

`tests/integration/support/` может оставаться для subprocess-помощников, используемых только integration-тестами. Не нужно перемещать их в общий support ради единообразия.
