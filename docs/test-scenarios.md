# Значимые тестовые сценарии «Контура»

Дата анализа: 29.09.2026. Исходная версия: 163dd93a21c00d9ab9a57dff0414d0a1065536f6.

Это проект критериев приёмки и карта рисков, а не новые автоматические тесты. Production-код и тестовый код не изменялись. Изучены README, docs/system.md, development-process.md, соответствующие разделы PROJECT_HISTORY.md, исходники сервера/клиента и тесты. Независимые проходы выполнены по пользовательскому процессу/хранению, CLI и покрытию/интерфейсу.

Главный вывод: основной путь и ряд механизмов восстановления проверены, но зелёный локальный набор не доказывает, что пользователь сможет получить результат через облако, пережить отказ хранилища или выйти из зависшего HTTP/фонового шага. Особенно важны классификация отказов Codex, сохранение пригодной версии, конечные сроки ожидания и восстановление на границах нескольких хранилищ.

**Как читать:** «требование» — явно описанный контракт; «факт» — поведение кода; «предложение Q…» — вариант, ещё требующий согласования. Наличие теста не делает закреплённое поведение правильным. «Нет» означает, что в изученном наборе не найден прямой сценарий, а не доказанное отсутствие любой косвенной проверки. «Частично» не считается закрытым критерием приёмки. Статические риски не выдаются за воспроизведённые дефекты.

## 1. Пользовательские процессы и границы системы

Основная задача человека: описать чистую синхронную TypeScript-функцию, дождаться её разработки и ревью двумя разными моделями, проверить конкретную версию, подтвердить её и получить совпадающие с одобрением файлы/ZIP.

В системе **одна незавершённая задача**, роли выполняются **последовательно**. Автор и применяющий по умолчанию используют gpt-6-sol, ревьюер — gpt-6-luna. Три агента выполняют разные роли; общий граф управляет порядком их вызовов. Следующий этап зависит от результата предыдущего, а применение — ещё и от решения человека. Общий граф и последовательность сами по себе не означают отсутствия самостоятельности агентов. Одновременно выполняющихся вызовов разных ролей сейчас нет: ошибка текущего шага блокирует запуск следующих; уже сохранённые результаты предыдущих ролей должны оставаться доступными. awaiting_approval и unknown_outcome также занимают единственный активный слот.

| Процесс | Путь от действия до результата | Критические зависимости и точки разрыва | Что необходимо сохранить |
| --- | --- | --- | --- |

Изменение произвольного существующего проекта, сеть/файлы внутри сгенерированной функции, сторонние зависимости, несколько активных задач и параллельные роли не входят в текущий продукт. Тестировать нужно понятный отказ/ограничение, а не выдумывать успешный сценарий за этими границами. Поддержка нескольких независимых серверов с разными каталогами/портами заявлена.

## 2. Реальные условия Codex и разные виды ограничений

### Режим интеграции

Используется локальный процесс codex exec с облачным вычислением модели, **не сервис Codex cloud tasks и не прямой вызов OpenAI SDK**. Передаются --json, --output-schema, --ephemeral, --ignore-user-config, --strict-config, read-only sandbox и запреты инструментов. Локальные инструменты запрещаются отдельно: один read-only сам по себе не означает отсутствия чтения файлов.

Приложение принимает строки входа ChatGPT и API key. Оно не сохраняет auth mode и не узнаёт тариф, баланс, сроки восстановления лимитов, workspace или действительность входа в облаке. Реальный способ входа текущего пользователя в этом анализе не проверялся; credentials не читались.

Официальная документация разделяет ChatGPT access и API-key usage-based access; локальный Codex CLI поддерживает оба. Действующая сессия может обновляться автоматически: само истечение короткоживущего access token не обязательно является отказом, в отличие от неуспешного refresh или отзыва доступа. [OpenAI: Authentication](https://learn.chatgpt.com/docs/auth).

Для входа ChatGPT нужен доступ тарифа/рабочего пространства именно к CLI и выбранным моделям. На дату анализа pricing указывает CLI и обе выбранные модели для Plus; ограниченный доступ Free/Go в desktop не доказывает доступ к данному CLI-процессу. API key использует API billing и доступные ключу модели; отдельная подписка ChatGPT для этого режима не является универсальным условием. Включённые лимиты и дополнительные кредиты — разные сущности; локальный reviewer здесь не является отдельным продуктом GitHub Code Review. [OpenAI: Pricing](https://learn.chatgpt.com/docs/pricing).

Официальные API errors различают rate limit, отсутствие prepaid credits, spend limits и usage limits; один 429 недостаточен для выбора действия. Некоторые billing errors имеют общий type insufficient_quota. Эти API сведения объясняют классы рисков, но **не доказывают конкретную форму JSONL ошибки в закреплённом Codex 0.156.1**, особенно при ChatGPT-входе. Нужны обезличенные реальные записи соответствующего режима. [OpenAI: Error codes](https://developers.openai.com/api/docs/guides/error-codes).

Документация CLI подтверждает JSONL и структурированные ответы, но схема JSON не является гарантией смысловой корректности функции. Поддержка всех перечисленных текущей документацией событий также не следует из проверки одной pinned-версии. [OpenAI: Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).

### Приёмка локального Codex — проект для обсуждения 02.10.2026

**Выбранный объём реализации:** по последующему решению пользователя от 02.10 в оставшееся время тестового задания приоритет ограничен сценарием login/logout и его защитными проверками. Результаты и границы этого исправления находятся в разделе «Исправление login/logout Codex» в [PROJECT_HISTORY.md](../PROJECT_HISTORY.md). Остальные критерии ниже сохраняются как предложения дальнейшей работы; это не заявление об их реализации. Затем пользователь расширила задачу: продолжение из сохранённого графа после повторного входа во время выполнения. Актуальный контракт этого случая — `awaiting_auth` и явное продолжение в [docs/system.md](system.md#проверка-подключения-к-codex); прежние строки матрицы об окончательном auth-error описывают исходную версию.

Уточнение цели от пользователя: важно проверить, как Codex реально работает и отказывает на компьютере, а не ограничиваться успешным набором внутренних тестов. 155 PASS от 29.09 подтверждают перечисленные assertions, но не заменяют такую приёмку. Ниже — отбор из матрицы по значимым пользовательским исходам, а не дополнительные почти одинаковые сценарии. Ожидаемое поведение, выходящее за текущий контракт, остаётся предложением Q01/Q02/Q03/Q06/Q09/Q12/Q14.

**Предлагаемый критерий готовности:** на заявленном компьютере человек может пройти от задания до скачивания через установленный Codex; при отказе он получает верную причину, сохранённые результаты и понятный способ продолжения. Вызовы, ожидание и расход попыток остаются управляемыми.

Базовая среда для первой приёмки — macOS, запуск штатной командой приложения, установленный CLI и сохранённый вход ChatGPT, как в ранее обсуждённом пользовательском пути. Конкретные версия ОС/архитектура, Node, путь и версия CLI должны войти в паспорт прогона. Код пока закрепляет /opt/homebrew/bin/codex и 0.156.1. Работу на других ОС/способах установки нельзя объявлять подтверждённой; API-key вход принимается парсером, но требует отдельной приёмки, если войдёт в поддерживаемый продукт.

Применимые G5–G10 проверяются на каждой роли, где различается сохраняемое состояние: у автора ещё может не быть версии; у ревьюера версия уже есть; у применяющего сохранено и решение человека. Нельзя закрыть весь критерий единственным 401 автора.

**Три разных доказательства, которые должны быть видны в отчёте:**

1. **Поведение приложения при управляемом отказе.** Исполняемый mock CLI даёт нужный сбой; настоящий адаптер, граф, хранилище и интерфейс проводят его до пользовательского результата. Это сильнее теста, где сразу бросили готовый CodexConnectionError, но установленный Codex всё ещё не проверен.
2. **Совместимость настоящего локального CLI.** Проверить бинарник, окружение запуска, отсутствие входа, credential-store доступность, реальный процесс и его завершение. Проверки version/login не вызывают модель. Полную работоспособность exec и cloud auth они не доказывают.
3. **Работоспособность с облаком через этот CLI.** Реальные роли с production-флагами, доступ к выбранным моделям, пригодный ответ, approval и ZIP; отдельно восстановление и отмена. Успешный ответ не доказывает классификацию всех возможных отказов.

**Предлагаемое правило приёмки:** не сводить эти доказательства к общему «тесты прошли». Отдельно показывать автоматические проверки, real local CLI и real end-to-end. Отсутствие CLI/входа/облака в обязательном real-прогоне — «условие среды не выполнено», не PASS и не незаметный переход на mock. Исторический успех помечается датой/версией. Сохранять role/attempt/phase/счётчик до и после, факт запуска/выхода процесса, hash версии/результата и время до прекращения ожидания; без tokens/credentials и полных личных логов.

Реальные негативные пробы планируются на выделенном пользователе/профиле или изолированном CODEX_HOME с доказанной изоляцией credential store. Сам по себе новый каталог не является достаточным доказательством отсутствия входа при OS keyring. Не переименовывать рабочий бинарник, не выполнять logout личного аккаунта и не копировать его credentials ради тестов. Разные версии можно проверять отдельными тестовыми установками; механизм выбора CLI-пути приложения пока требует решения Q12.

В официальной документации подтверждены разные credential stores и использование сохранённого входа в exec, а также исключение config.toml флагом --ignore-user-config. Это обосновывает проверку G2; совместимость конкретной pinned-версии и сочетания настроек всё равно требует real-пробы. [Authentication](https://learn.chatgpt.com/docs/auth), [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode), проверены 02.10.2026.

Открытые решения для ближайшего обсуждения: (1) продолжение текущей задачи после исправимого отказа — рекомендовано в G10, ожидается выбор пользователя; (2) поддерживаемая установка — только фиксированный путь/версия либо настраиваемый явно выбранный бинарник; (3) конечные сроки ожидания и Stop с учётом HTTP/записей, а не одного CLI таймера; отдельно от Stop существующей задачи — отмена ещё не завершённой команды создания. До этих решений не закреплять спорное поведение новым тестовым кодом. На 02.10 новые прогоны CLI/моделей не выполнялись.

## 3. Общие профили ожидаемого исхода

Профиль в колонке «результат» является частью каждого сценария: он задаёт UI, задачу/роль, срок, сохранность, повторы, восстановление, дубли и влияние на остальные роли. Отступления указаны в строке. Нельзя закрывать сценарий проверкой одного только исключения.

| Профиль | Наблюдаемый результат и статус | Срок окончания ожидания | Частичные данные и продолжение | Повтор, дубли, остальные роли |
| --- | --- | --- | --- | --- |
| B — отказ до команды | Понятная причина readiness/валидации; создание не произошло, либо старое состояние/approval/бюджет не изменились; новая попытка роли отсутствует | CLI: каждый --version/login status ограничен 2 с, readiness имеет дедлайн 5 с; завершение группы может добавить около 1 с. Общего HTTP SLA нет — Q03 | Старые задачи/файлы доступны; исправить установку/вход/ввод и повторить команду | Автоповтора mutation нет; тот же creation key не создаёт вторую задачу. Следующая роль не запускается |
| K — известный отказ роли | error, активная попытка → failed, понятная причина и следующий шаг; результат не объявляется готовым | После распознанного отказа и завершения CLI; верхняя практическая граница вызова около 180 с + завершение/запись, но не доказанный общий SLA — Q03 | Последняя целая версия, ревью, решение и история сохраняются; сейчас продолжения error нет, нужна новая задача — Q02 | Автоповтора нет; новая задача расходует новый бюджет и может повторять облачную работу. Следующие роли не выполняются, предыдущие результаты не стираются |
| U — исход внешнего вызова неизвестен | unknown_outcome, последняя попытка unknown, активная снята; предупреждение о возможном повторном вызове, доступен явный retry | Предупреждение 30 с; timeout 180 с либо обнаруженный разрыв. ## 5. Матрица условий зависимостей и сбоев на границах

Для D01–D16 обязательны применимые точки: (а) причина уже существует до создания/approve/retry; (б) появилась после предварительной проверки, до запуска конкретной роли; (в) во время ответа; (г) после содержательного ответа, до turn.completed/close/checkpoint. **B до команды применим только к локально обнаруживаемым условиям.** Уже исчерпанная облачная квота, отзыв сессии или отсутствие model access могут пропускаться local readiness: задача/approval/reservation будут созданы, затем фактический вызов даст K/U и прикладная попытка уже потрачена. Не нужно искусственно повторять «нет CLI» после уже запущенного процесса: там проверяется потеря возможности запустить **следующую** роль. Для crash consistency минимальный набор контрольных точек: перед reservation; после reservation до spawn; после turn.started; после structured output до завершения CLI; после сохранения revision до event/checkpoint; после checks до checkpoint; после decision event до approval checkpoint; перед result rename; после rename до publication event; после event до completed checkpoint. Проверить автора/reviewer/applier там, где различаются сохраняемые данные и допустимое продолжение. Убийство в одном месте не покрывает все эти окна.

## 10. Критические сценарии для признания системы работоспособной

Это обязательный набор разных рисков, а не требование запускать все редкие combinations перед каждым изменением.

1. **Сквозной реальный путь:** собственная задача → две выбранные модели → независимая оценка результата → точное approval → applier → скачиваемые файлы; J01/J08/J19.
2. **Понятный отказ до работы:** missing/incompatible CLI, нет входа, исправление причины, история доступна; J02/J03, D01–D03.
3. **Облачные условия:** действительность сессии, доступ к каждой модели, временный rate limit против quota/credits/context; D04–D15. Без реальной совместимости форматов mock coverage недостаточен.
4. **Непригодный код не становится результатом:** V, J09–J12, M09–M11; отдельно слабые self-tests и независимые ожидаемые результаты.
5. **Конечное ожидание и отмена:** J13/J20/J21, D16/D19/D30; после failure/Stop нет живого бесконтрольного шага и скрытого следующего вызова.
6. **Одна команда — один эффект:** J05/J14/J16 и X03–X06; учитывается потерянный ответ и reload, а не только double click.
7. **Надёжное подтверждение/публикация:** D22/D24/D27 и X08; сохраняются ровно одобренные байты, повреждённые не скачиваются.
8. **Восстановление без скрытого облачного повтора:** J22/J25, D21/D23/D25/D35; reservation и бюджет переживают рестарт.
9. **Изоляция:** единственная активная задача/владелец данных, запрет смешивания real/mock, запрет инструментов и обхода путей; J07/J26, D32, M05/M07.
10. **Пользователь может управлять после частичного отказа:** здоровые данные читаются, stale UI честен, сохранённая пригодная версия не теряется; D25/D30 и Q02/Q03/Q05.

Пункты 3, 5, 6 и 8 сейчас закрыты лишь частично. Для неизвестных требований сначала утвердить oracle, затем писать тесты: иначе получится автоматическое закрепление спорного поведения.

## 12. Сценарии, которых в существующем наборе не хватает

Группы с прямым пробелом, а не только необходимостью более широкого повторения:

- Классификация billing/credits/usage/rate/context по реальным CLI сообщениям и по режиму входа; refresh/revocation и потеря доступа именно у reviewer/applier: D04–D12.
- Вечный POST и end-to-end Stop deadline, timeout сохранения observation, cleanup после успешного CLI: D19/D30/D34, M14.
- Ошибка index/task event/SQLite на точных границах создания, approval и graph completion: D21–D23, X06; состояния preparing/pending без живой работы.
- JSONL null, формы primitive/array, отсутствие финальных markers/newline, двойной output, exec output limits и много мелких событий: D17/D18, M03/M06.
- Возобновление пригодной версии после известных отказов и исчерпание бюджета прямо перед applier: J23/X07.
- Матрица Stop во всех ролях, проверках и публикации; 429/Stop, retry/Stop, approve/reject двух вкладок: J20/J21, X01–X08.
- Создание после потерянного ответа с reload, доступность preview, stale artifact response: J06/J15, M15.
- Повреждённый индекс/отдельный checkpoint/середина JSONL, неполный перенос, result без revisions, transient read failure готового результата: D25–D27, X13, Q16.
- Отдельные реальные средовые зависимости: CLI path/upgrade, clean install, worker launch/runtime availability, диск/FD/нагрузка/сон, orphan CLI: J01/D20/D28/D29/D31/D35.
- Семантическая независимость acceptance от автора/ревьюера, строгость чистоты и parity JSON в QuickJS/Node: J11, M09/M10.
- Полные браузерные failure journeys, accessibility, loopback threat model, миграции: M13–M21.

Частично покрытые механизмы нельзя вычёркивать из плана: например, проверенный torn tail не покрывает повреждённую полную строку, а approve дважды не покрывает противоположные решения двух вкладок.

По замечаниям уточнены статус инфраструктурного отказа runner/хранения, облачные причины до локального preflight, неверная schema applier, отказ spawn exec после readiness и startup recovery до проверки занятого порта. Это редактура критериев, не исправление production-дефектов.

## 15. Независимый заключительный проход

**При каких реалистичных условиях все текущие тесты пройдут, но пользователь не сможет выполнить основную задачу?**

| Условие | Почему зелёный набор этого не исключает | Как проявится у человека | Сценарии, которые закрывают риск |
| --- | --- | --- | --- |
| CLI установлен другим способом или автоматически обновлён | Mock subprocess не проверяет production path/версию на новой машине | Форма не запускает агентов, хотя codex в обычном терминале работает | J01/J02, D01/D02 |
| Login сохранён, но reviewer-модель недоступна, сессия отозвана или квота аккаунта потрачена в другом приложении | npm run check не обращается в облако; успешный local readiness не является cloud readiness | Автор уже дал код, результат нельзя довести до готовности; новая задача может повторить тот же отказ | D04–D10, J23, X11 |
| Провайдер/CLI вернул иной формат отказа или JSONL null | Синтетические тесты покрывают выбранные сообщения и события | Неверный совет retry либо авария backend, вместо понятного отказа | D17, M03/M06, E1 |
| Рабочий диск заполнился на index или decision event | Тестовые temp-каталоги исправны; идемпотентность без I/O fault проходит | Вечный preparing или недоступное подтверждение; новая задача заблокирована | D21/D22, E3/E4 |
| SQLite временно отказал после выполнения узла | Ошибка diagnostic logger — другая зависимость | Экран показывает работающего агента, процесса уже нет; обычный resume недоступен | D23, M12, E7 |
| HTTP POST или сохранение observation не завершилось | Обычные mocks возвращают success/error, а не вечный pending | Вечное ожидание/disabled Stop, несмотря на заявленные таймауты модели | D19/D30, E2/E5 |
| Backend погиб, прежний Codex остался жив | Mock port recovery проверяет checkpoint, не живой orphan облачного CLI | Повтор может создать лишний расход и конкурирующий облачный запрос | D35, Q14 |
| Автор и ревьюер разделяют ошибочное допущение, слабые авторские cases проходят | Независимые fixtures проверяют конкретный известный дефект вне production | ZIP скачан и «одобрен», но функция не решает реальную задачу | J11, M09/M10, Q10 |
| Валидная сложная задача породила большой код/JSON/диагностику | Простые fixtures далеки от нескольких взаимодействующих лимитов | Reviewer не стартует либо предлагается бессмысленный retry того же большого запроса | D11/D12/D18, X14 |
| Целый result остался, но revisions повреждены; либо одна старая БД-запись недоступна | Тесты порчи результата не равны потере черновика/одного checkpoint | Нельзя скачать целый результат или открыть приложение вообще | D25/D27, X13, E6/E9 |
| Ответ создания потерян, reload стер key | Идемпотентность проверена при сохранённом key в живом hook | После завершения первой задачи повтор создаёт вторую и тратит лимит | J06, X06 |
| История выросла, одновременно открыты несколько вкладок, filesystem медленный | Маленькие изолированные тестовые данные и быстрый диск | Список/Stop/readiness задерживаются, основной путь фактически недоступен | D28/D30, Q03/Q11 |

Этот проход не требует считать всякую гипотезу уже обнаруженным дефектом. Его результат — конкретные наблюдаемые критерии и условия проверки, которые должны дополнять успешные локальные тесты.
