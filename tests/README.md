# Тесты приложения

## Запуск

- `npm test` — воспроизводимые unit/integration-проверки без облачных вызовов.
- `npm run check` — линтер, TypeScript, локальные тесты и сборка.
- `npm run test:e2e` — настоящий браузер Chrome и HTTP-сервер, mock-ответы моделей.
- `QA_REAL_CODEX=1 npm run test:e2e` — тот же путь браузера с настоящими автором, ревьюером и применяющим агентом через локальную авторизацию Codex.
- `npm run test:live-review` — смешанная проверка: замоканная версия с намеренной ошибкой, затем настоящее ревью и исправление через Codex. Проба сохраняет происхождение ответов в отчёте.
- Восстановление SQLite проверяется двумя отдельными запусками `test:workflow-probe` с аргументами, как показано ниже.

E2E самостоятельно собирает приложение и запускает сервер на `127.0.0.1:4318`. `QA_E2E_PORT` меняет порт. Работающий чужой сервер не переиспользуется. Каждый запуск получает отдельный временный каталог; после закрытия сервера он удаляется. Нужен установленный Google Chrome. Настоящий режим включается явно, использует существующий вход ChatGPT и лимиты подписки; скрытого перехода на mock нет.

## Проверка восстановления SQLite между процессами

Первый процесс сохраняет резервирование вызова автора и останавливается перед подтверждением. Второй открывает ту же базу и продолжает граф без повторного автора. Проба требует три аргумента: этап, путь SQLite и путь счётчика вызовов.

Запускайте из корня проекта:

```sh
probe_dir="$(mktemp -d "${TMPDIR:-/tmp}/two-model-workflow-probe.XXXXXX")"
npm run test:workflow-probe -- start "$probe_dir/checkpoints.sqlite" "$probe_dir/author-calls.txt"
npm run test:workflow-probe -- resume "$probe_dir/checkpoints.sqlite" "$probe_dir/author-calls.txt"
```

Оба процесса должны завершиться успешно и вывести `authorCalls: 1`; второй также показывает `phase: "complete"`. После проверки временную папку можно удалить:

```sh
rm -r -- "$probe_dir"
```

## Где читать сценарии

- `unit/` — контракты, QuickJS, хранилище, Codex CLI, модель истории и клиентские хуки.
- `integration/` — взаимодействие настоящих модулей, диск, SQLite, HTTP/SSE и перезапуск процессов.
- `e2e/` — создание задачи, роли, перезагрузка перед решением и скачивание точного результата.
- `support/` — временные ресурсы, ожидание состояния, запуск E2E-сервера и данные экрана.
- `fixtures/` — входные случаи и явно замоканные ответы.
- `live/` — отдельно запускаемые проверки с настоящим Codex.

[Карта сценариев](scenario-map.md) связывает все 87 исходных выполнений с текущими тестами. Количество увеличено за счёт разделения и новых клиентских/форматных проверок.

## Как устроен читаемый тест

Существенные данные находятся в самом тесте. Подготовка, проверяемое действие и сравнение разделены пустыми строками. Название сообщает условие и ожидаемый результат. Каждая функция и callback пояснены по-русски. Помощники скрывают только техническую подготовку и очистку; создание задачи, решение, остановка, перезапуск и ожидания остаются видимыми.

Mock-проверки контролируют ветки, которые настоящая модель не обязана воспроизводить: задержки, отсутствие ответа, неверный результат, повторное ревью. Они не являются доказательством подключения к облаку. Проверки хранения и QuickJS выполняют настоящий локальный код.

Исторические E0/E2-отчёты, JSONL и stderr в `unit/` — сохранённые свидетельства предыдущих версий. Они не входят в `npm test` и не подтверждают текущую реализацию.
