# Уточнение: локальная отладка и экономия собственного кода с LangGraph JS

Дата проверки: 24.09.2026. Входы: brief.md, research.md, research-loop-options.md. Только документальное исследование первичных источников; установки и прогоны не выполнялись. Исследование отказов, транспорта и ограничения контекста ведёт координатор. Этот документ уточняет прежнюю рекомендацию, но не фиксирует выбор пользователя.

## Пересмотр рекомендации

Возражение пользователя обосновано. Прежний аргумент «сценарий небольшой, поэтому свой координатор проще» не учитывал объём механики сохранения, возобновления, ожидания человека и диагностических средств. Наличие прикладных проверок, остающихся при любом подходе, не отменяет экономию на готовом движке.

По исследованной части рекомендую **LangGraph JS как библиотеку + локальный SQLite checkpointer + собственные узлы предметного сценария**, с текстовым интерфейсом и без обязательного Studio/LangSmith. Это готовый механизм оркестрации с адаптацией под задачу. Свой координатор остаётся альтернативой при выявленной несовместимости транспорта или если реальные интеграционные проверки покажут чрезмерную сложность. Документальных оснований утверждать, что собственный вариант быстрее или содержит меньше ошибок, сейчас нет; численные оценки строк и часов не делались.

## Что доступно в библиотеке без сервера

| Возможность | Что проверено | Польза и границы |
|---|---|---|
| Текущее состояние | `getState(config)` возвращает snapshot последнего или указанного checkpoint: значения, следующие узлы, время, metadata, tasks с ошибками/interrupts. [Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers) | Основа команды «статус»; не нужно самостоятельно проектировать generic snapshot API. |
| История | `getStateHistory(config)` возвращает checkpoints от новых к старым; `updateState` создаёт новый checkpoint. [Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers) | Можно исследовать переходы и причины паузы; это история состояний, а не автоматически полный транспортный журнал. |
| Локальные события выполнения | JS `stream` имеет режимы `values`, `updates`, `debug`, `custom`. Debug показывает узел и состояние; `config.writer` позволяет передавать собственные события. [Первичный исходник streaming docs, JS-секции](https://raw.githubusercontent.com/langchain-ai/docs/main/src/oss/langgraph/streaming.mdx) | Можно построить текстовый вывод без облачного tracing. Для внешнего Codex-процесса события JSONL нужно явно преобразовывать в custom events; внутренние вызовы не станут видны автоматически. |
| Схема графа | `getGraphAsync().drawMermaid()` выдаёт Mermaid-текст; `drawMermaidPng()` в документированном варианте использует Mermaid.ink API. [Graph API](https://docs.langchain.com/oss/javascript/langgraph/use-graph-api#visualize-your-graph) | Текстовую схему можно хранить и отображать локально. PNG-помощник нельзя безоговорочно называть offline. Схема показывает топологию, а не историю конкретного запуска. |
| Повтор и ветвление | Исторический checkpoint можно передать в `invoke`; `updateState` позволяет создать альтернативную ветку. Узлы после выбранной точки выполняются повторно, включая обращения к моделям и interrupts. [Time travel](https://docs.langchain.com/oss/javascript/langgraph/use-time-travel) | Полезно для разбора дефектов и сравнения решений. Это повтор исполнения, не воспроизведение записанного видео и не отмена файловых эффектов. Для диагностического повтора использовать тестовый адаптер/изолированный проект. |
| Постоянное состояние | SQLite checkpointer — отдельный официальный пакет для локальных workflows; режим `durability: "sync"` сохраняет checkpoint перед следующим шагом. [Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers) | Переиспользуем persistence и выбор следующего шага; не разрабатываем собственный движок checkpoints. |
| Ожидание человека | `interrupt` + `Command({ resume })` + стабильный thread ID сохраняют паузу и позволяют продолжить. Узел с interrupt запускается сначала. [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts) | Готовая долговечная пауза, но содержимое запроса и связь approval с версией — наши. |

Вывод «без сервера» основан на локальных примерах Graph API: они создают и вызывают объект графа внутри приложения. LangSmith там предложен как дополнительное средство отладки, а не предпосылка выполнения. Никакой отдельный LangSmith-аккаунт для этих библиотечных API не указан. [Graph API setup](https://docs.langchain.com/oss/javascript/langgraph/use-graph-api#setup). Отключение tracing в реальном окружении всё равно надо проверить: ранее выставленные переменные или callbacks могут его включать.

## Studio, локальный Agent Server и LangSmith — разные части

**Studio** — веб-интерфейс визуального взаимодействия с Agent Server API. Он показывает архитектуру, пройденные узлы, промежуточные состояния, потоки задач и time travel; поддерживает локальный сервер и размещённый сервис. Сам объект библиотеки в обычном CLI не становится доступен Studio без серверного API. [Studio overview](https://docs.langchain.com/langsmith/studio).

Для документированного локального маршрута используются `npx @langchain/langgraph-cli dev` и браузерный UI на `smith.langchain.com`, подключённый к localhost. В local quickstart среди prerequisites указан LangSmith API key, получаемый через регистрацию. Поэтому стандартный путь со Studio следует планировать с аккаунтом и дополнительным серверным процессом; не обещать полностью автономный offline GUI. Docker для dev-сервера не требуется. [Local development](https://docs.langchain.com/langsmith/local-dev-testing).

Отправка traces в LangSmith отключается `LANGSMITH_TRACING=false`; официальный Studio quickstart утверждает, что при этом данные не уходят с локального сервера. Это заявление о tracing в данном сценарии, а не доказательство отсутствия любых сетевых соединений: UI загружается с сайта, а наши модели облачные. Safari имеет ограничение подключения к localhost; документация предлагает tunnel. Для локального демо на Mac разумнее сначала проверить другой браузер, не добавляя туннель как обязательный компонент. [Studio quickstart](https://docs.langchain.com/langsmith/quick-start-studio).

**LangSmith tracing** — дополнительное сохранение и исследование трасс во внешней системе; его не нужно смешивать с локальным `streamMode: "debug"`. Документированный quickstart Studio приводит debugger-примеры с Python/debugpy; они не являются подтверждением готовой настройки пошагового JS-debugger. Для TypeScript нужна отдельная настройка Node debugger, если она вообще потребуется. [Studio quickstart](https://docs.langchain.com/langsmith/quick-start-studio).

## Какие обязанности действительно снимаются

Это сравнение инженерных обязанностей, а не утверждение, что тесты приложения исчезают.

| Область | Собственный координатор | LangGraph + SQLite | Проверки нашего приложения в обоих вариантах |
|---|---|---|---|
| Checkpoints и переход после restart | Проектировать сериализацию, схему хранения, сохранение курсора, загрузку и продолжение | Подключить saver, schema/reducers, thread ID и нужную durability; использовать готовый runtime | Перезапуск с тем же ID, сохранность результатов, правильный следующий шаг |
| Ожидание человека | Собственный persisted pending-state, обработка решения и продолжения | Готовые interrupt/resume и сохранение payload | Отказ/молчание не применяет код; подтверждена именно показанная версия |
| Инспекция выполнения | Формат snapshots, запрос истории и отображение проектируем сами | API snapshot/history и stream уже есть; пишем узкое отображение | Статусы понятны оператору; ожидание модели отличается от ожидания человека |
| Диагностическое ветвление | Отдельно разрабатывать, если решим включить | Готовые replay/fork | Изоляция внешних эффектов и недопущение применения старого approval |
| Бизнес-логика | Своя | Свои nodes и transitions | Правильные роли, ревью, ограничители, контроль версии |
| Codex и файлы | Свои адаптеры | Те же адаптеры внутри nodes | Доставка, неизвестный исход, бюджет входа, точное применение, частичная запись |

LangGraph не нужно тестировать заново как библиотеку во всём объёме. Нужно проверить выбранную конфигурацию и наши границы взаимодействия. Документация предлагает Vitest, отдельный checkpointer на тест, проверку узлов и графа; часть изолированных node-тестов не проверяет persistence. Поэтому положительный unit-тест узла не заменит прерывание реального процесса и повторное открытие SQLite. [Testing guide](https://docs.langchain.com/oss/javascript/langgraph/test).

## Практическая рекомендация для обсуждения

Основной кандидат — библиотечный LangGraph с локальными state/history/debug и фиксированным графом; Studio оставить необязательным средством разработки. Так экономия на persistence/HITL доступна сразу и не зависит от облачного инструмента диагностики. Если пользователь хочет именно визуальную отладку, отдельно включить локальный Agent Server + Studio и проверить аккаунт, браузер, настройки tracing и соответствие поведения запуска основному CLI.

До реализации остаётся выбрать стабильную версию и проверить её API: открытая документация/main может опережать релиз. Успешная работа после аварии, совместимость SQLite-драйвера с MacBook и фактическое отсутствие отправки traces пока не доказаны прогоном. Уточнение координатора о современных timeout/errorHandler/drain дополнительно усиливает готовый вариант; детальная проверка этих механизмов относится к его исследованию отказов.
