# Исследование решений

Дата: 24.09.2026. Основание: ТЗ 0.3 согласовано пользователем. **Рекомендация для обсуждения; архитектура ещё не утверждена.**

## Уточнение после обсуждения 24.09.2026

После более детального сравнения преимущество собственного координатора не подтвердилось. Текущая рекомендация — **LangGraph JS + локальный SQLite-checkpointer + адаптер Codex**. Причина: сохранение/возобновление, паузы для человека и просмотр истории относятся к обязательной работе, и библиотека снимает их механическую реализацию. Общая прикладная логика не отменяет эту экономию. Подробности в [новом сравнении](research-langgraph-comparison.md). Выбор пользователем ещё не зафиксирован.

## Первоначальная рекомендация (заменена уточнением выше)

Небольшой последовательный координатор на TypeScript, локальная SQLite и адаптер установленного `codex exec --json`. Три роли: автор → ревьюер → подтверждение человека → применяющий агент. При замечаниях — возврат автору с сохранённым общим лимитом. Один процесс координатора управляет переходами; модели не выбирают самостоятельно бесконечную цепочку следующих вызовов.

Это инженерная рекомендация для фиксированного небольшого сценария, а не результат тестирования работающего контура. Она минимизирует число понятий, которые нужно реализовать и объяснить на демонстрации.

## Что установлено

- Codex CLI 0.156.1 установлен; `codex login status` сообщает об активном входе ChatGPT. Есть выбор модели, JSONL и структурированный финальный ответ. Неинтерактивный режим повторно использует сохранённую авторизацию. [Официальная документация](https://learn.chatgpt.com/docs/non-interactive-mode).
- В локальном каталоге от 24.09.2026 видны разные модели, включая `gpt-6-sol` и `gpt-6-luna`. Предлагаем их как начальных кандидатов для автора и ревьюера; применяющий агент может использовать Sol. Успешный вызов каждой модели ещё не проверен.
- Получить живой список через App Server в текущей среде не удалось: запуск требует записи служебной SQLite-базы в `~/.codex`, которая здесь ограничена. Это ограничение проверки, а не доказательство недоступности моделей. Документация `model/list` рекомендует получать доступные варианты для конкретного аккаунта. [App Server](https://learn.chatgpt.com/docs/app-server).
- SQLite позволяет атомарно сохранять изменения внутри БД. Запись исходников и облачные запросы не становятся частью этой транзакции. [SQLite](https://sqlite.org/atomiccommit.html).
- Node v26.9.0 и npm 11.19.1 доступны. Драйвер SQLite и версии зависимостей ещё не выбраны; `node:sqlite` требует оценки статуса API выбранной версии. [Node SQLite](https://nodejs.org/api/sqlite.html).

Секреты не читались; установки, изменения приложения и реальные вызовы моделей не выполнялись. Детали команд и источники: [исследование Codex](research-codex.md).

## Сравнение

| Вариант | Что получаем | Что всё равно нужно сделать | Оценка для этой задачи |
|---|---|---|---|
| Свой небольшой координатор + SQLite | Явные этапы и транзакционное сохранение | Переходы, журнал сообщений, общий лимит, восстановление и подтверждение версии | Рекомендуется: небольшой фиксированный сценарий |
| LangGraph JS + SQLite checkpointer | Граф, checkpoints, interrupts | Доказательство доставки, компактный вход, общий бюджет между запусками, проверка версии | Полезен при росте числа ветвей; сейчас добавляет зависимости |
| OpenAI Agents SDK JS | Handoffs, ограничения run, сериализация пауз и approvals | Те же прикладные гарантии и отдельная проверка совместимого доступа | Свободная передача управления здесь не нужна; это не Codex SDK |

Источники и подробное сравнение: [независимое исследование](research-loop-options.md), [LangGraph persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence), [LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts), [Agents SDK approvals](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/).

Для подключения к Codex есть и официальный [Codex TypeScript SDK](https://learn.chatgpt.com/docs/codex-sdk). Он остаётся альтернативой адаптеру CLI, если работа с процессом и событиями окажется сложнее библиотечного вызова. App Server для основного контура пока не рекомендуется: его более широкий протокол не нужен для текстового интерфейса.

## Как предлагаем обеспечить требования

| Требование | Предлагаемый способ | Что показать на приёмке |
|---|---|---|
| R-04: остановка | Сохранённый общий счётчик вызовов, срок ожидания каждого вызова, явная причина остановки | Зациклить роли; перезапустить; убедиться, что бюджет не обнулился |
| R-05: наблюдаемость | Для каждого сообщения сохранять ID, роль, модель, время, подтверждённые этапы и связь с ответом | Подавить ответ и показать возраст ожидания, отсутствие ответа и известную границу доставки |
| R-06: продолжение | Сохранить актуальную функцию, тесты, последнее ревью, этап и ограничения; новый вызов получает только этот пакет | Прервать процесс, продолжить ту же задачу, измерить вход; старый архив не доступен для чтения агентом |
| R-18: применение | Подтверждение относится к версии кода и исходному состоянию файлов; третий агент инициирует проверенное применение сохранённых байтов | Отказ/молчание не меняет файлы; изменение версии или базы делает подтверждение недействительным |

Это предложения, а не уже реализованные гарантии. Численные лимиты фиксируются в плане. Рабочий кандидат бюджета прикладного входа — 32 KiB UTF-8, с явной остановкой при превышении. Этот размер не равен всему внутреннему контексту Codex: системные инструкции и дополнительные чтения нужно учитывать отдельно; нельзя доказать требование одним измерением нашего prompt.

## Существенные решения перед планом

1. **Путь доступа:** сохранённый вход Codex, без извлечения токенов и без отдельного API-ключа. После выбора решения ранняя проверка двумя короткими реальными вызовами должна подтвердить доступ и события; кэш моделей не заменяет эту проверку.
2. **Третья роль:** настоящий агент, который может запросить применение конкретного одобренного артефакта. Запись выполняет узкий проверяемый механизм; свободная правка кода после подтверждения не допускается. Реализацию этого инструмента определить в плане.
3. **Неизвестный исход вызова:** сохранять неопределённость и продолжать с последнего подтверждённого этапа после явного действия оператора; не запускать скрытые бесконечные повторы. Повтор учитывается в общем бюджете. Гарантии единственного удалённого вызова нет.
4. **Восстановление применения:** если процесс оборвался между записью файлов и отметкой в базе, сверить фактические файлы с одобренной версией. Для нескольких файлов возможна частичная запись, которую нужно выявить и отобразить; нельзя объявить успех только по завершению агента.

## Оставшиеся неизвестные и ограничения

- Реальная доступность выбранной пары моделей, задержки и достаточность лимитов аккаунта.
- Точная граница подтверждения «дошло»: запуск процесса не означает приём облачной моделью. Предлагаем явно различать приём локальным адаптером, события выполнения и полученный ответ; смысл статуса закрепить до реализации.
- Отключение лишнего контекста/инструментов и изоляция каталога истории в конкретной версии CLI требуют проверки.
- Срок сдачи из исходника остаётся 03.10.2026; часовой пояс и канал передачи репозитория ещё не подтверждены.
- В Git пока нет коммитов. Реальную историю следует начать на ближайшем этапе и продолжать по мере работы, не создавать задним числом фиктивные этапы.
