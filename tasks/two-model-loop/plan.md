## 1. Что строим

Локальное приложение для MacBook: браузерный интерфейс, один Node.js backend, LangGraph и готовый `SqliteSaver`, облачные модели через сохранённую аутентификацию Codex. Команды идут через HTTP, обновления — через SSE. Backend обслуживает собранный frontend; отдельные очереди, облачная база, LangSmith и Studio для запуска не нужны.

Пользователь создаёт задачу текстом или выбирает один из трёх примеров, наблюдает работу агентов, проверяет предложение, подтверждает либо отклоняет его и получает файлы в отдельной папке задачи. Одна активная задача; история доступна для просмотра. Применение в существующий пользовательский проект исключено.

## 2. Два разных набора агентов

**Агенты продукта** работают внутри будущего приложения с пользовательской функцией:

| Роль | Предлагаемая модель | Работа и ограничения |
|---|---|---|
| Автор | `gpt-6-sol` | Готовит `solution.ts` и проверки логики; исправляет замечания. Отдаёт структурированный кандидат, не публикует результат |
| Ревьюер | `gpt-6-luna` | Получает конкретную версию, задание и результаты тестов; возвращает одобрение или конкретные замечания. Не меняет файлы |
| Применяющий агент | `gpt-6-sol` | После решения человека получает только одобренную версию; возвращает запрос публикации этой версии. Backend проверяет разрешение и записывает точные одобренные байты |

Третий агент действительно вызывается; он не должен заново сочинять код. Если его ответ содержит другую версию или изменения, публикация отклоняется. Автор и ревьюер обязаны иметь разные model IDs; молчаливое переключение на одну модель запрещено. Эти назначения — кандидаты из исследования, доступность проверяется в E0.

**Агенты разработки** создают само приложение:

| Исполнитель | Предлагаемая модель | Ответственность |
|---|---|---|
| Координатор | Текущая модель диалога | Решения с пользователем, задания, интеграция, общие документы состояния |
| Планировщик | `gpt-6-astra` | Контракты, последовательность и границы работ |
| A — граф и общая основа | `gpt-6-sol` | Общие типы/конфиги, LangGraph, API, запуск приложения |
| B — Codex и файлы | `gpt-6-sol` | Транспорт моделей, версии артефактов, проверки и публикация |
| C — интерфейс | `gpt-6-sol` | React-экраны и взаимодействия пользователя |
| QA | `gpt-6-astra` | Независимые приёмочные сценарии и прогоны |
| Reviewer | `gpt-6-astra` | Независимое ревью интегрированной версии |

Назначения моделей команды предлагаются для согласования, не описывают фактическую текущую конфигурацию. Текущие planner и QA наследуют модель сессии. Ограничение «две модели, три агента» относится к продукту, а не числу разработчиков. Основания для будущей настройки — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) и [Model selection](https://developers.openai.com/api/docs/guides/model-selection): для реализации стартовать с Sol medium, для узких задач Luna high; Astra для независимой проверки — наша стратегия, не результат сравнительного теста. Тарифы API не переносим на использование подписки Codex.

## 4. Контракты компонентов

Общие сериализуемые контракты фиксируются A в E1. Схемы входов и результатов проверяются на границах процесса и HTTP; frontend не импортирует серверные модули.

| Контракт | Минимальное содержимое |
|---|---|
| `TaskState` | `schemaVersion`, `taskId`, задание, назначения моделей, фаза, текущая версия, последнее ревью, результат проверок, подтверждение, счётчики/лимиты, активная попытка, причина остановки |
| `ArtifactRef` | ID задачи и версии, разрешённые относительные пути, SHA-256 каждого файла, хеш manifest всей версии |
| `Attempt` | Уникальный ID, роль/модель, ID входной версии, начало, подтверждённые события процесса, завершение/ошибка/неизвестный исход |
| `Review` | ID и хеш проверенной версии, `approved` или `changes_requested`, список замечаний |
| `Approval` | ID решения, точный хеш версии, решение пользователя и время; повтор того же решения идемпотентен |
| `Event` | Последовательный номер задачи, ID события/попытки, время, тип, отправитель/получатель, краткое содержимое, ссылка на артефакт |
| `CodexPort.run` | Роль, model ID, ограниченный контекст, схема ответа, `AbortSignal`; поток наблюдаемых событий и структурированный итог |
| `ArtifactStore` | Записать неизменяемую версию, проверить хеши, подготовить рабочую копию, опубликовать подтверждённую версию, получить файл по ID |
| `CheckRunner` | Получает версию; возвращает статус компиляции и тестов, ошибки и длительность; без полномочий публиковать результат |

Граф — единственный владелец переходов. Фазы для UI: подготовка, автор, проверка, ревью, ожидание подтверждения, применение, завершено, остановлено, ошибка, неизвестный исход. Технические узлы подготовки/завершения внешнего вызова могут быть отдельными, хотя UI показывает одну роль.

Последовательность: подготовить попытку и сохранить её → вызвать автора → сохранить версию → проверить → ревью → доработка либо `interrupt` → подтверждение → третий агент → публикация → сверка и итоговая проверка. Лимит проверяется до нового вызова; подготовка попытки и расход бюджета фиксируются отдельным шагом с синхронным durable checkpoint до внешнего действия (`durability: sync`, поддержку выбранной версией проверить в E0). Счётчик не обнуляется при restart.

`interrupt` располагается в узле без побочных действий. Возобновление этого узла не повторяет автора, тесты или публикацию. После отказа задача завершается с явным статусом «отклонено», без результата; изменение задания создаёт новую задачу.

## 5. API и переподключение интерфейса

| Запрос | Результат |
|---|---|
| `GET /api/tasks` | Список задач и актуальные статусы |
| `POST /api/tasks` | Текст задания; `202` с task ID; повтор с тем же ключом идемпотентности не создаёт вторую задачу |
| `GET /api/tasks/:id` | Снимок состояния, роли, версии, разрешённые действия и номер последнего события |
| `GET /api/tasks/:id/events` | SSE; восстановление через `Last-Event-ID`/курсор |
| `POST /api/tasks/:id/decision` | Решение и хеш показанной версии; устаревшее подтверждение → `409` |
| `POST /api/tasks/:id/stop` | Идемпотентная остановка, отмена активного Codex/проверки |
| `POST /api/tasks/:id/resume` | Продолжение сохранённого этапа; неизвестный исход требует явного выбора повтора, без скрытого нового запроса |
| `GET /api/tasks/:id/artifacts/:artifactId` | Предпросмотр или скачивание разрешённого файла |
| `GET /api/tasks/:id/result.zip` | Комплект подтверждённых файлов |

Backend слушает loopback, проверяет Origin команд и не принимает произвольный путь файла от браузера. Один процесс-владелец данных; второй запуск отказывается работать с той же папкой. Активная задача и проверки определяются сервером, а не открытой вкладкой.

Для восстановления SSE используем небольшой файловый журнал значимых событий каждой задачи (`events.jsonl`), который **не управляет графом**. Сохраняем старт/исход попытки, передачу версии и сообщения ролей; текстовые фрагменты потока допускается объединять, без обещания восстановления каждого токена. Завершённый ответ хранится целиком. Запись события предшествует отправке в браузер; при обрыве последней строки читается только полная запись. События повторяемых узлов имеют устойчивые ID для исключения дублей.

Клиент получает снимок и курсор, подписывается на события после курсора, исключает дубли. При пропуске недоступной части истории сервер требует новый снимок. Перезапуск backend сверяет незавершённые попытки с журналом и checkpoint; неизвестное не превращается в «успешно». Запуск локального Codex не обозначается как доказанная доставка облачной модели.

## 6. Артефакты и выполнение проверок

Предлагаемый корень данных — `.local-data/` в корне проекта, исключённый из Git. Внутри: `checkpoints.sqlite` и `tasks/<id>/{revisions,work,result,events.jsonl}`. Перенос истории требует базы вместе с артефактами; пользователю для результата достаточно `result` или ZIP.

Версия пишется в временную соседнюю папку, проверяется и атомарно переименовывается; затем ссылка попадает в checkpoint. После сбоя допустима неиспользуемая версия, но недопустима ссылка на частично записанную. Manifest хранит хеши функции и тестов; имя задачи и пути задаёт сервер. Симлинки, выход из корня и произвольные имена запрещены.

Публикация: проверить approval и хеш → подготовить `result` во временной папке на том же диске → сверить байты → rename → сохранить завершение графа. При сбое после rename сверка того же manifest завершает операцию без повторной записи. Существующий результат с иным хешем вызывает конфликт, а не перезаписывается.

Первая версия исполняет только чистые синхронные TypeScript-функции с сериализуемыми входами и выходами; без сети, файлов, процессов, сторонних зависимостей и произвольных package scripts. Это техническое ограничение предлагается согласовать. Минимальный тестовый контракт: имя экспортируемой функции и случаи `{name, args: JsonValue[], expected: JsonValue}`, сравнение результата по структуре. Тестовый файл создаётся доверенной обвязкой из этих случаев; допустимые импорты фиксированы. Текст задания не разрешает shell-команды или установку зависимостей. Поддержка асинхронности, произвольного тестового кода и проверок побочных эффектов не входит.

В E0 проверяем готовую изолированную JS-среду, например QuickJS/WASM без host bindings, с ограничением времени и памяти после транспиляции TypeScript. Это кандидат только при быстрой подтверждаемой совместимости, не обязательная зависимость и не отдельный проект runtime. `node:vm` и обычный дочерний Node-процесс не считаются защитой. Если готовая среда не поддерживает сценарии, выносим решение о фиксированном runner с allowlist импортов и доступными ограничениями Node/macOS, явно описав остаточный риск; обычный subprocess не выдаём за полноценную изоляцию. До решения E0 произвольный сгенерированный код не запускается. Codex также работает без свободного доступа к архиву, целевой папке и инструментам записи; это проверяется отдельно.

E0 — ранний барьер: при недоступности второй модели или несовместимости сохранения основная реализация не начинается. Не заменяем библиотеку или аутентификацию без обсуждения. Проверки разных рисков E0 разрешено проводить параллельно; E1 зависит от их результатов. Файлы экспериментов E0 размещаются только в перечисленных областях соответствующих владельцев, без новой общей папки. Настоящие переписки, журнал решений и история работы собираются начиная с E0; на E5 их комплектуют, а не воссоздают задним числом.

Параллельные волны при четырёх слотах: координатор + A/B/C на E2; координатор + A/B/QA на E3; координатор + QA/Reviewer на E4. QA может заранее подготовить сценарии до появления приложения, а исполняет их после интеграции. Назначения каждой волны включают базовый commit, документы, cwd, файлы и доказательство готовности.

Последовательно обязательны: согласование плана → E0 → фиксация общих контрактов E1 → параллельная реализация → интеграция → фиксация commit → независимые прогоны/ревью → исправления и повтор затронутых проверок → сдача. Внутри продукта последовательно идут ревью версии → approval этой версии → публикация.

| Целостность | Удаление/подмена артефакта блокирует продолжение; сбой до/после rename не даёт частичный или повторно изменённый результат |

Тесты механики используют fake adapter без расходов на модели; доступ к моделям и полный пользовательский путь проверяются отдельно настоящими вызовами. Успех на имитации не предъявляется как доказательство облачной интеграции. Reviewer отдельно проверяет границы файлов, идемпотентность и отсутствие второго самописного движка состояния.

## 9. Предлагаемые настройки и вопросы согласования

Числа ниже — стартовые предложения, а не требования исходного задания:

- До 3 версий функции: первый вариант и 2 доработки; до 7 вызовов моделей суммарно, включая применение. Каждая новая попытка, в том числе после неизвестного исхода, расходует лимит.
