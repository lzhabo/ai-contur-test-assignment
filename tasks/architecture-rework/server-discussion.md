# Обсуждение серверной структуры

Статус: компактная группировка принята ответом пользователя «окей». Детали переноса истории в SQLite остаются открытыми. Реализация не начата.

## Обязанность не требует собственной папки

Первоначальное предложение слишком подробно раскладывало технические обязанности по верхнему уровню. Их можно сохранить в небольших файлах, группируя вокруг задач приложения. Число папок само по себе не определяет качество архитектуры.

## Ответы по существующей реализации

- `http`: название обозначало всё общение с браузером — Express routes, ошибки, SSE и выдачу frontend. Можно назвать `routes`, а сборку Express оставить в `app.ts`. Типы внутренних ошибок задач принадлежат задачам; перевод в HTTP status — маршрутам.
- Публичные операции задач: обычные функции, которые вызывает код маршрутов — создать, прочитать, подтвердить/отклонить, остановить, повторить неизвестный вызов. Это не новый внешний API или отдельный сервис. Формулировку заменяем на «операции с задачами».
- Snapshot: текущий ответ `GET /api/tasks/:id` для фронтенда. Включает задачу/этап, роли, текущую версию, проверки/ревью, доступные действия, файлы, события и номер последнего события. Формируется по запросу; отдельный архив таких HTTP-ответов не ведётся. Сохранённое состояние LangGraph в SQLite — отдельное понятие. Возможное имя функции: `getTaskDetails`.
- `workflow`: здесь находится последовательность автор → проверка кода → ревью → решение человека → применение и возвраты при замечаниях. Предлагается `tasks/agent-loop.ts` для графа с отдельными небольшими файлами выполнения шагов и восстановления. LangGraph сохраняется.
- `checks`: проверяет сгенерированную функцию во время выполнения задачи. Текущий код выполняет диагностику TypeScript и тестовые случаи в QuickJS с лимитами времени/памяти. ESLint анализирует правила исходного кода и не заменяет выполнение функции с ожидаемыми результатами. Возможное название — `code-runner`, отражающее изолированное исполнение кода; это не папка тестов самого приложения.
- `events`: сохраняет пользовательскую историю задачи — начало попытки, создание версии, замечания, решение человека, результат. Сейчас это `tasks/<id>/events.jsonl`, а не только сообщения в памяти; SQLite уже сохраняет checkpoints графа. История нужна для интерфейса и после перезапуска, даже локально. Её код можно разместить в `storage/task-history.ts`; отдельная верхняя папка `events` необязательна.
- `observability`: техническая диагностика для разработчика — вход/выход узлов, сохранение checkpoint, восстановление, ошибки. Сейчас есть `server-events.jsonl` и обвязка checkpointer. Это отличается от истории для пользователя. Предлагается `logger.ts` и размещение диагностической обвязки рядом с graph/persistence. Самостоятельный верхний раздел необязателен. Нужную существующим проверкам диагностику сохраняем; расширение мониторинга не требуется.

ESLint: [официальное описание](https://eslint.org/docs/latest/use/core-concepts/). Пример различия: `sum(a, b) { return a - b; }` может быть корректным по типам и правилам оформления, но не проходит проверку `sum(2, 3) === 5`. Успешные тесты доказывают только проверенные случаи, а не правильность для всех входов.

## Более компактная группировка для обсуждения

```text
server/
  index.ts               запуск и закрытие
  app.ts                 сборка Express
  config.ts              настройки сервера
  logger.ts              технические диагностические записи
  routes/                endpoints, HTTP errors, SSE, frontend fallback
  tasks/                 операции, данные для экрана, цикл агентов, восстановление
  codex/                 настоящий вызов модели и mock-исполнение
  code-runner/           проверка и изолированное выполнение созданной функции
  storage/               checkpoints, индекс, история и файлы результата
```

Эта группировка согласована; конкретный состав файлов уточняется в плане. Содержимое `tasks` и `storage` делится на несколько файлов по обязанностям; объединение папок не означает объединение всего кода в один файл.

## Хранение истории

Предлагается обсудить таблицу истории задач в SQLite: task ID, sequence, event ID, время, тип, полезные данные. После сохранения запись отправляется браузеру; при переподключении недостающие записи читаются по sequence. Соблюдаем уникальность event ID, порядок, replay/live без дублей и запись до отправки.

Вариант SQLite объединяет способы хранения состояния и истории, но сам по себе не создаёт общей транзакции с LangGraph checkpointer. Нужно определить подключение/схему и поведение при сбое; нельзя обещать атомарность без реализации и проверки. Перенос старого JSONL зависит от ещё не согласованной совместимости прежних данных. Альтернатива — оставить JSONL и только перенести файл реализации в `storage`.

Подключение Sentry в будущем можно рассматривать для диагностики; история, которую приложение показывает пользователю, должна оставаться доступной через собственное хранилище приложения.
