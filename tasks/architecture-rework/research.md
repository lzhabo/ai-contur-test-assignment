## 2. Что стоит изменить в нашем приложении

- `src/web/App.tsx`: HTTP, SSE, polling, отмена запросов, защита от старых ответов, команды и отображение находятся вместе. Файл всего 177 строк, но длинные JSX-строки скрывают объём обязанностей. Один лимит строк эту проблему не решит.
- `src/server/workflow/service.ts`: 340 строк; одновременно индекс задач, сериализация команд, запуск и отмена графа, восстановление, проверка результатов и DTO для браузера. Нужны внутренние модули с понятными обязанностями и небольшой общей внешней поверхностью.
- `src/server/workflow/graph.ts`: 215 строк; нужно отделить инструкции/сборку контекста и исполнение роли от описания связей графа, сохранив границы checkpoint.
- `src/shared/`: рядом лежат браузерные DTO, внутреннее состояние, серверные ports и конфигурация с `process.env`. Предлагается оставить общими только действительно общие схемы и данные.
- Express routes уже вызывают `AppService`. Здесь нужна адресная декомпозиция SSE, ошибок и маршрутов, а не новая абстракция над Express.
- `artifacts/local-store.ts` создаёт текст `solution.test.ts`, а `checks/quickjs-runner.ts` извлекает случаи регулярным выражением из этого шаблона. Предлагается общий внутренний codec формата, сохраняющий существующие экспортируемые байты; изменение формата хранения тестовых случаев — отдельное решение.

## 3. Правила примера и предлагаемый перенос

| Правило `range-interview/AGENTS.md` | Предложение для нашего приложения |
| --- | --- |
| Одна причина изменения на production-файл | Принять. Делить по обязанности: запросы, состояние, отображение, восстановление, хранение |
| Небольшой интерфейс модуля, детали внутри | Принять. Вынесение функции полезно, если оно скрывает отдельную обязанность, а не просто пересылает аргументы |
| Dependencies передаются явно; создание в composition root | Принять. Серверный bootstrap собирает Codex, QuickJS, файлы, журнал и persistence; браузерный entrypoint — API client и QueryClient. Внутренние детали модуля остаются закрытыми |
| Review после 200 строк, split до 250; exported functions около 40 строк | Адаптировать как ориентиры ревью. Форматировать нормально, описывать исключения; не дробить связный алгоритм ради чисел |

| `client/api` → hooks → components | Принять; компоненты не вызывают `fetch`/`EventSource`. Текст формы, выбранный файл и раскрытые блоки остаются локальным UI-state |
| TanStack Query для remote state | Рекомендовать для списка, snapshot, файлов и команд; SSE требует отдельной интеграции и тестов порядка обновлений |
| Тонкие Express routes | Принять: разобрать и проверить запрос → вызвать операцию → сериализовать результат. HTTP-коды сопоставлять с ошибками приложения на HTTP-слое |
| Комментарии объясняют инварианты и решения | Принять. Особенно для reserve-before-call, восстановления, approval и публикации |
| Тесты используют интерфейс вызывающего кода | Принять с учётом слоя: HTTP и команды — для поведения продукта; внутренний граф — для checkpoint/crash recovery |
| `npm run check` до итогового commit | Принять: lint, typecheck, обычные tests и production build. E2E — отдельный обязательный шаг приёмки; live-пробы запускаются отдельно |
| Domain terms transaction/query/cursor/applied filters | Заменить словарём приложения: задача, роль, попытка вызова, версия, ревью, решение пользователя, результат, событие |

Они не обосновывают изменения нашего продукта. Текущий стек и версии Express-базы — исходная точка; обновления зависимостей рассматриваются отдельно.

## 4. Предлагаемая структура

```text
src/
  client/
    api/                 HTTP, схемы ответов, подключение SSE
    hooks/               чтение задач, команды, синхронизация SSE и cache
    components/          отображение и локальное состояние элементов
    workflow/            модель и отображение истории/графа
    App.tsx              сборка экрана
    main.tsx             создание общих зависимостей браузера
  shared/
    api/                 DTO запросов, ответов, событий и Zod-схемы
    examples/            общие тексты заданий
  server/
    main/                конфигурация, сборка зависимостей, запуск/закрытие
    http/                Express, routes, SSE, ошибки, SPA
    tasks/               публичные операции задач и snapshot для клиента
    workflow/            LangGraph, контекст ролей, вызовы и восстановление
    storage/             индекс задач, SQLite/checkpointer, data lock
    codex/               реальные и mock вызовы
    artifacts/           версии файлов, integrity, публикация и ZIP
    checks/              TypeScript и QuickJS
    events/              сохранённый журнал событий
    observability/       диагностические логи
```

Внутренние типы и ports живут рядом с серверными модулями, которые определяют их смысл. `shared` не импортирует Node.js, Express, LangGraph или окружение процесса. Browser не импортирует server.

`http → tasks → workflow` — направление вызовов. `tasks` принимает команды, контролирует единственную активную задачу и отдаёт представление состояния. `workflow` управляет порядком шагов и своим восстановлением через LangGraph. Хранилища и внешние операции передаются через необходимые интерфейсы. Второй самостоятельный движок переходов не создаётся.

Границы файлов внутри этих папок определяются планом и конкретными интерфейсами. Не требуется отдельный interface/repository/factory для каждой функции. Реальные варианты уже есть у Codex: настоящий процесс и mock-исполнение.

## 5. Клиент и SSE

Рекомендуемый вариант: TanStack Query владеет серверными данными, React — локальными элементами формы. SSE сообщает о необходимости обновить snapshot и список; snapshot остаётся источником отображаемого состояния, сервер — источником разрешённых действий.

Нужны явные правила:

- Cache key включает task ID; для файлов — artifact ID и hash версии.
- Ответ по старой выбранной задаче не заменяет новую; соединение и запросы освобождаются при уходе с экрана.
- Переподключение сохраняет семантику cursor/Last-Event-ID; bursts событий объединяются в согласованное обновление.
- Сохраняется существующая защита от snapshot с меньшим `lastEventSequence`; это свойство не приписывается Query автоматически. При равном cursor нельзя запрещать все обновления: состояние checkpoint может измениться без нового события.
- Polling остаётся резервным способом получить состояние; потеря SSE показывается отдельно от успеха/ошибки задачи.
- Для create сохраняется Idempotency-Key на повтор одной попытки; автоматический повтор изменяющих команд выключен. Resume неизвестного вызова требует явного действия пользователя.

Альтернатива: те же границы `api/hooks/components` без новой библиотеки. Зависимостей меньше, но cache, отмена, объединение обновлений и состояние команд остаются собственным кодом. Предлагается обсудить выбор до установки пакетов.

## 6. Что сохраняем при переработке

1. Две разные модели, три роли, одна активная задача; подтверждение относится к точной версии и manifest hash.
2. `prepare*` сохраняет попытку и бюджет до `call*`. Переименование узлов и формат checkpoint затрагивают recovery и совместимость данных.
3. Неизвестный исход не становится успехом и не запускает скрытый повтор. Режимы real/mock не продолжают задачи друг друга.
4. Проверки QuickJS, ограничения контекста, версии и общего числа вызовов, отмена и stop/publish races.
5. Сохранение события до отправки, replay/live SSE без дублей, работа после restart.
6. Неизменяемые версии, проверка hash, безопасные пути, публикация подтверждённых байтов, ZIP и обнаружение повреждения результата.
7. HTTP paths, payloads и коды ошибок Express-базы. В том числе её исторически необычные ответы 500 на некоторые ошибки body parser; менять их в рамках структурного рефакторинга не предлагается.
8. Пользовательский путь, история ревью, граф процесса, mock-сценарии и диагностические доказательства.

## 7. Совместимость данных и порядок работы

Предлагается сохранить формат checkpoint и имена узлов на первом этапе. Новая реализация получает собственную папку данных. Проверки чтения/возобновления старых задач выполняются на копиях fixture-данных; существующие `.local-data` используются исходными версиями и не подключаются одновременно к новой.

Нужно согласовать, должна ли новая версия обязательно открывать и продолжать все ранее созданные задачи. Это влияет на критерии приёмки; совпадение TypeScript-типов само по себе не доказывает совместимость checkpoint.

После согласования: повторно проверить Express HEAD/status, записать согласованный base SHA, создать отдельную `codex/architecture-rework` и отдельный worktree. Сохранить исходные checkout и ветки, перенести сюда документы задачи. Затем подготовить план с владельцами файлов и проверками по `workflow/PROCESS.md`. Переход к реализации следует согласованному плану.

Существующие unit/integration/HTTP/E2E-тесты Express-версии сохраняются как доказательства поведения. При переносе модулей можно менять import/setup, но нельзя удалять сценарии ради зелёного прогона. Добавляем проверки нового разделения клиентского состояния: старый ответ, смена задачи, burst/reconnect SSE, повтор команды. Структурные подробности тестируем только там, где они сами являются инвариантом восстановления.
